[39] Design Requirements
[40] Xác định yêu cầu của khách hàng thế nào?
[41] Xác định rõ yêu cầu chức năng và phi chức năng
[42] Scalability: Có thể mở rộng để phục vụ nhiều user.
[43] Performance: Đáp ứng nhanh, latency thấp.
[44] Availability: Đảm bảo uptime cao, ít downtime.
[45] Security: Bảo mật dữ liệu, xác thực, phân quyền.
[46] Maintainability: Dễ sửa, dễ nâng cấp.
[47] Reliability: Hoạt động ổn định, ít lỗi.
[48] Cost: Giới hạn chi phí triển khai/vận hành.
[49] Compliance: Tuân thủ quy định pháp luật
[50] Xác định các ràng buộc quan trọng về nghiệp vụ - business (giảm chi phí, tăng số lượng user...), ràng buộc kĩ thuật (dùng công nghệ nào) và ràng buộc về tích hợp với các hệ thống khác.
[51] Đề xuất giải pháp, hướng tiếp cận dựa trên yêu cầu đó.
[52] Nguyên lý CAP
[53] Là nguyên lý quan trọng trong thiết kế hệ thống phân tán.
[54] CAP stands for:
[55] + Consistency tức là mọi node trong hệ thống đều nhất quán về dữ liệu tại một thời điểm
[56] + Availability là hệ thống luôn sẵn sàng đáp ứng mọi request
[57] + Partition Tolerance là khả năng chịu phân mảnh mạng, tức là hệ thống vẫn hoạt động (không bị sập toàn bộ) khi có sự cố các node không liên lạc được với nhau do chia cắt mạng
[58] Một hệ thống phân tán chỉ có thể đảm bảo 2 trong 3 yếu tố trên cùng một lúc. Trong thực tế luôn phải đảm bảo Partition Tolerance do sự cố mạng là không thể tránh khỏi. Còn việc ưu tiên CP hay AP tùy thuộc vào tính chất của hệ thống phân tán, ví dụ ngân hàng ưu tiên tính nhất quán chọn CP, mạng xã hội ưu tiên tính sẵn sàng (dữ liệu cập nhật chậm một chút cũng không sao) chọn AP.
[60] Networking
[61] Các khái niệm cần nhớ
[62] Firewall: kiểm soát, cho phép hoặc chặn luồng dữ liệu vào ra hệ thống / thiết bị
[63] NAT – network address translation: kĩ thuật chuyển đổi các địa chỉ IP trong mạng private sang IP công cộng (có thể dùng chung cho các thiết bị trong mạng nội bộ giúp tiết kiệm địa chỉ IP) và ngược lại
[64] CORS: Cross-Origin Resource Sharing là một cơ chế của trình duyệt web chặn truy cập tài nguyên từ một domain khác với domain hiện tại.
[65] Ví dụ frontend và backend API triển khai ở 2 domain khác nhau, backend cần cho phép CORS để frontend có thể gọi API và lấy dữ liệu.
[66] Giao thức mạng theo tầng
[67] Có 7 tầng OSI nhưng thực tế developer chủ yếu quan tâm các tầng: Application, Transport, Network
[68] Application Layer: xử lý logic, giao tiếp user và app/service.
[69] Giao thức:
[70] + HTTP/HTTPS: giao thức nền tảng cho web và API, dùng để truyền dữ liệu giữa client và server
[71] Cơ chế: request/response - client gửi request, server trả về dữ liệu json, file...
[72] Các phương thức: GET - lấy dữ liệu, POST - tạo mới dữ liệu, PUT/PATCH - sửa dữ liệu, DELETE - xóa dữ liệu.
[73] Các HTTP status code chia thành các nhóm:
[74] 2xx: thành công, thường gặp nhất là 200 OK
[75] 3xx: chuyển hướng - redirection
[76] 4xx: lỗi từ client, thường gặp là
[77] 400 Bad Request: Request sai cú pháp, dữ liệu đầu vào không hợp lệ.
[78] 401 Unauthorized: Chưa xác thực hoặc token không hợp lệ.
[79] 403 Forbidden: Không có quyền truy cập resource này.
[80] 404 Not Found: Không tìm thấy resource hoặc endpoint.
[81] 5xx: lỗi từ server, thường gặp là
[82] 500 Internal Server Error: Lỗi server, không xác định rõ nguyên nhân
[83] 502 Bad Gateway: Gateway hoặc proxy nhận được phản hồi không hợp lệ từ server phía sau.
[84] 503 Service Unavailable: Dịch vụ tạm thời không hoạt động (quá tải, bảo trì).
[85] 504 Gateway Timeout: Gateway hoặc proxy không nhận được phản hồi từ server phía sau đúng thời gian.
[86] HTTPS là HTTP kết hợp phương thức mã hóa SSL/TLS, đảm bảo bảo mật, tránh bị nghe lén, hầu hết các dịch vụ production hiện nay đều yêu cầu HTTPS.
[87] + FTP (truyền file)
[88] + SSH (truy cập server qua command)
[89] + SMTP (giao thức gửi email)
[90] + WebSocket (kết nối 2 chiều real-time giữa client và server sau khi handshake)
[91] + RPC (dùng trong microservices giao tiếp giữa các dịch vụ do latency thấp)
[92] Transport Layer: đảm bảo truyền dữ liệu từ nơi gửi đến nơi nhận.
[93] Giao thức: TCP (kết nối tin cậy, thường dùng cho web, API), UDP (kết nối nhanh nhưng không tin cậy, dùng cho streaming, game).
[94] Network Layer: định tuyến dữ liệu qua các mạng khác nhau.
[95] Giao thức: IP (định danh địa chỉ thiết bị), ICMP (ping, kiểm tra kết nối), ARP (tìm MAC của IP).
[97] API Design
[98] Một thiết kế API tốt đảm bảo:
[99] Đơn giản và nhất quán
[100] Tất cả các endpoint đều có cấu trúc rõ ràng, đặt tên nhất quán, ví dụ như /users/{id}/orders để dễ dàng hiểu được chức năng và resource mà API cung cấp.
[101] Tuân thủ chuẩn giao tiếp như RESTful, GraphQL, gRPC...
[102] Ví dụ đối với RESTful API:
[103] + Sử dụng đúng các phương thức HTTP (GET, POST, PUT, DELETE…).
[104] + Trả về đúng mã trạng thái HTTP (200, 201, 400, 404, 500…).
[105] Dễ mở rộng, bảo trì
[106] Versioning để dễ quản lý các phiên bản API: /v1/users, /v2/users
[107] Tài liệu rõ ràng
[108] Sử dụng Swagger/OpenAPI để tự động hóa và cập nhật tài liệu, giúp dev và đối tác dễ tích hợp, test API.
[109] Bảo mật
[110] Sử dụng HTTPS, xác thực qua JWT hoặc OAuth2, và kiểm soát quyền truy cập, hạn chế rate limit để bảo vệ API khỏi tấn công.
[111] Các mô hình API
[112] REST
[113] Stateless (không lưu trạng thái giữa các request, mỗi request là độc lập).
[114] Sử dụng các HTTP method chuẩn như GET, POST, PUT, DELETE.
[115] Dễ bị over-fetching (lấy dư dữ liệu) hoặc under-fetching (lấy thiếu dữ liệu).
[116] Trao đổi dữ liệu chủ yếu bằng JSON, dễ đọc cho con người.
[117] GraphQL
[118] Tránh được vấn đề over-fetching và under-fetching (client chỉ lấy đúng dữ liệu cần), tuy nhiên khó trong caching.
[119] Query dựa trên schema xác định kiểu dữ liệu rõ ràng.
[120] Query phức tạp có thể ảnh hưởng hiệu năng server.
[121] Chỉ dùng phương thức POST.
[122] Luôn trả về HTTP 200, nếu có lỗi sẽ nằm trong payload gửi về kèm.
[123] gRPC
[124] Xây dựng trên HTTP/2, hỗ trợ multiplexing và server push.
[125] Dùng Protocol Buffers để truyền dữ liệu, rất hiệu quả và tiết kiệm băng thông.
[126] Hiệu năng cao, phù hợp cho hệ thống lớn hoặc microservices.
[127] Dữ liệu ít thân thiện với con người, khó đọc trực tiếp.
[128] Yêu cầu môi trường/phần mềm hỗ trợ HTTP/2.
[130] Caching & CNDs
[131] Caching
[132] Là việc lưu trữ tạm thời dữ liệu ở các tầng gần với người dùng hơn như trình duyệt, proxy hoặc server (redis) để phục vụ nhanh các request hay sử dụng.
[133] Giảm truy vấn tới backend và db, tiết kiệm tài nguyên và tăng hiệu năng.
[134] Áp dụng tốt cho REST vì dữ liệu thường ít thay đổi (không phù hợp GraphQL).
[135] CDN
[136] Là mạng lưới phân phối các máy chủ đặt ở nhiều nơi trên thế giới. Lưu các file tính như HTML, CSS, JS, ảnh để người dùng tải nhanh từ server gần nhất. Giúp tăng tính high availability, tăng độ trễ khi yêu cầu tài nguyên và tăng bảo mật.
[138] Proxy Server
[139] Là thành phần trung gian giữa client và server, có vai trò chuyển tiếp request và response.
[140] Chức năng chính:
[141] + Ẩn IP thực của client hoặc server, tăng bảo mật
[142] + Lọc, kiểm soát, ghi log các truy cập
[143] + Cache dữ liệu tăng tốc truy cập cho client
[144] Hai loại chính:
[145] + Forward proxy:
[146] Đứng trước client (giữa client và internet).
[147] Giúp ẩn IP của client khỏi các server ngoài, server chỉ thấy IP của proxy.
[148] Thường dùng để kiểm soát truy cập web (chặn Facebook, Youtube) trong nội bộ công ty.
[149] + Reverse proxy:
[150] Đứng trước server (giữa server và internet)
[151] Ẩn IP của server backend, client chỉ thấy IP của proxy.
[152] Thường dùng để load balancing - phân phối đều request cho các server phía sau, xử lý mã hóa SSL giảm tải cho backend, caching hoặc nén dữ liệu trả về.
[153] Các load balancer như Nginx, AWS ELB hay CDN như Cloudflare, AWS CloudFront cũng được coi là reverse proxy.
[155] Load Balancer
[156] Là thành phần trung gian giúp phân phối đều lưu lược request từ client đến nhiều server backend phía sau. Ví dụ AWS Elastic Load Balancer, Nginx...
[157] Mục tiêu là tối ưu hiệu năng, tăng tính chịu tải và đảm bảo hệ thống hoạt động ổn định.
[158] Các loại LB:
[159] + Layer 4 (Transport): Phân phối dựa trên địa chỉ IP, port (ví dụ: TCP, UDP). Nhanh hơn, phù hợp các dịch vụ không cần xử lý sâu về nội dung như cân bằng tải cho database, các ứng dụng TCP.
[160] + Layer 7 (Application): Phân phối dựa trên nội dung HTTP/HTTPS, URL, cookie… (ví dụ: Nginx, HAProxy). Phù hợp cho web và API.
[161] Các thuật toán LB chính:
[162] Round Robin: Chia đều theo lượt từng server.
[163] Least Connection: Ưu tiên server rảnh nhất (ít kết nối nhất).
[164] IP Hash: Dựa vào IP client, giữ session đảm bảo client luôn được chuyển đến 1 server cố định.
[165] Weighted (Weighted Round Robin / Weighted Least Connection): Chia theo sức mạnh từng server (gán trọng số cho từng server).
[166] Sticky session: Đối với hệ thống có cân bằng tải, nếu không dùng thuật toán IP hash nhưng vẫn muốn gắn 1 client với 1 server (ví dụ như lưu giỏ hàng, ứng dụng chat hoặc trạng thái đăng nhập trên các hệ thống cũ) thì dùng sticky session (được hỗ trợ trong hầu hết các LB như Nginx, HAProxy, AWS ELB)
[167] Nếu backend stateless, không lưu session trên backend mà lưu ở client hoặc lưu tập trung tại Redis/Memcached thì không cần dùng sticky session. Ví dụ như hiện nay các ứng dụng web đều dùng JWT, session được xác nhận thông qua token (lưu phía client), server không cần nhớ trạng thái của user, hay hệ thống microservices, session lưu trên Redis, mọi server đều truy cập được.
[169] Message Queue (Kafka, RabbitMQ, ActiveMQ)
[170] Là thành phần trung gian giúp các hệ thống hoặc microservices giao tiếp bất đồng bộ với nhau, thông qua việc gửi và nhận thông điệp (message)
[171] Giao tiếp bất đồng bộ: Ví dụ khi người dùng đăng ký xong, hệ thống trả về thông báo thành công ngay. Việc gửi email xác nhận được gửi như một message vào MQ (Kafka, RabbitMQ...). Service chuyên gửi mail sẽ nhận message này và xử lý sau. Do vậy người dùng không cần chờ email gửi xong mới được đăng ký thành công.
[172] Kafka
[173] Có thể xử lý dữ liệu với thông lượng (throughput) lớn, tốc độ cao, lưu trữ message lâu dài (có thể đọc lại nhiều lần, replay lại message), được thiết kế để scale tốt phù hợp với hệ thống phân tán
[174] Phù hợp cho hệ thống cần nhiều sự kiện liên tục, như streaming log, phân tích dữ liệu realtime, hoặc nhận dữ liệu từ hàng ngàn thiết bị IoT
[175] RabbitMQ
[176] Dễ dùng, triển khai nhanh, hỗ trợ nhiều giao thức, mạnh về hàng đợi nghiệp vụ. Message không được lưu trữ lâu dài như Kafka
[177] Phù hợp cho các ứng dụng cần xử lý bất đồng bộ như e-commerce, gửi email, thanh toán, nhập đơn hàng...
[178] ActiveMQ
[179] Tích hợp với hệ sinh thái Java
[180] Hỗ trợ nhiều kiểu giao tiếp như point-to-point, pub-sub
[182] Scenario
[183] Một hệ thống hàng triệu người dùng thiết kế thế nào? Những điểm quan trọng để tối ưu hệ thống đó.
[184] Scale Horizontally
[185] Triển khai nhiều instance backend (EC2, container, server vật lý) phía sau LB
[186] Stateless server: không lưu trạng thái trên server (JWT), session lưu ở cache ngoài (Redis)
[187] Load Balancer
[188] AWS ALB, Nginx, HAProxy
[189] Sử dụng health check để tự động loại instance lỗi khỏi hệ thống
[190] Database Scalability
[191] Read Replica: ghi vào master/primary, đọc dữ liệu từ slave/replica database
[192] Sharding/Partitioning: chia dữ liệu thành nhiều phần nhỏ theo user, khu vực... tránh quá tải trên một node
[193] Connection Pooling: Hạn chế số lượng kết nối (tránh quá tải), tái sử dụng được kết nối nên tăng hiệu năng, tiết kiệm tài nguyên
[194] Caching
[195] Cache tầng ứng dụng: Dùng Redis
[196] Cache tầng CDN (AWS CloudFront)
[197] Xử lý bất đồng bộ (Asynchronous Processing)
[198] Queue/ Massage Broker: Kafka, RabitMQ, SQS, ActiveMQ
[199] Worker pool: tăng số thread để xử lý song song
[200] High Availability & Fault Tolerance
[201] Triển khai đa vùng (multi-zone, multi-region): nếu 1 vùng gặp sự cố, các vùng khác vẫn hoạt động
[202] Auto-Scaling: Tự động tăng giảm số lượng instance dựa vào tải thực tế
[203] Replica, backup: Đảm bảo dữ liệu không mất khi server/db có sự cố
[204] Connection Management
[205] Hạn chế timeout, tối ưu giữ kết nối lâu (keep-alive), dùng connection pool, áp dụng cho cả backend và database
[206] Rate limiting: hạn chế số request của mỗi user/IP trên một đơn vị thời gian để bảo vệ hệ thống
[207] Monitoring, Logging, Alerting
[208] Realtime monitoring: Theo dõi chỉ số CPU, RAM, IOPS (số lượng thao tác đọc ghi IO trên giây), số lượng request, response time...
[209] Alerting: cảnh báo khi có dấu hiệu quá tải, lỗi dịch vụ
[210] Log tập trung: thu thập log để phân tích và xử lý sự cố nhanh
[211] Một luồng request-response client đi qua các thành phần của một hệ thống web application hiện đại thế nào (ví dụ triển khai với React.js, Spring Boot, AWS)?
[212] Lưu ý (với sơ đồ dưới):
[213] CloudFront vừa có thể dùng làm CDN cho file tĩnh (React app) vừa có thể làm reverse proxy, bảo vệ và tăng tốc API.
[214] AWS WAF có thể áp dụng ở cả CloudFront, ALB, hoặc API Gateway để bảo vệ hệ thống khỏi các tấn công web phổ biến.

[222] Database
[223] Overview
[224] DB types
[225] Relational DB (SQL): Là loại database tổ chức data thành các bảng với các hàng và các cột, có cấu trúc rõ ràng. Đảm bảo tính nhất quán, toàn vẹn dữ liệu.
[226] Ví dụ như PostgreSQL, MySQL, Oracle.
[227] Use cases:
[228] + Hệ thống cần dữ liệu quan hệ phức tạp
[229] + Dữ liệu ổn định, ít thay đổi cấu trúc
[230] + Muốn đảm bảo tính nhất quán và toàn vẹn dữ liệu (ACID)
[231] + Cần truy vấn phức tạp JOIN, transaction đảm bảo.
[232] Hệ thống ngân hàng, quản lý đơn hàng...
[233] NoSQL (non-relational database): Là loại database tổ chức dữ liệu linh hoạt (ví dụ MongoDB – document, Redis – key value, Cassandra -  column based, Neo4j – graph), không yêu cầu schema cố định, dễ mở rộng ngang (horizotal scalability), tối ưu cho lưu trữ lớn, tốc độ cao
[234] Use cases:
[235] + Dữ liệu phi cấu trúc, hoặc thay đổi thường xuyên (user profile, log, session).
[236] + Hệ thống cần scale lớn, real-time (social network, IoT, gaming).
[237] + Không cần JOIN phức tạp, chủ yếu lấy/gửi dữ liệu đơn giản.

[240] Data Normalization (Chuẩn hóa)
[241] Là quá trình tổ chức dữ liệu trong database nhằm giảm thiểu sự dư thùa (redundancy) và đảm bảo tính nhất quán (consistancy) của dữ liệu.

[244] Ví dụ vi phạm:

[251] Denormalization

[255] Indexing
[256] Index giống như mục lục của cuốn sách, giúp tìm nhanh tới trang cần tìm thay vì lật từng trang.
[257] Cách hoạt động:
[258] + Khi tạo index trên một hoặc nhiều cột, CSDL sẽ tạo ra một cấu trúc dữ liệu riêng như B-Tree hoặc Hash Table.
[259] + Khi truy vấn dựa trên các cột được lập index, CSDL sẽ tra chỉ mục đó thay vì quét toàn bộ bảng (full table scan)
[260] Các loại phổ biến:
[261] + Index 1 cột
[262] + Composite index (nhiều cột)
[263] + Unique index (đảm bảo giá trị không trùng lặp)
[264] + Fulltext index: hỗ trợ cho văn bản với LIKE, tìm kiếm có % ở phía trước.
[265] Ví dụ tìm tất cả khách hàng có tên kết thúc bằng chữ “an”. Với index thông thường là B-Tree index, nó sẽ chỉ tìm từ đầu chuỗi, vì thế việc tìm từ khóa match ở cuối chuỗi buộc CSDL phải full table scan. Giải pháp lúc này là dùng fulltext index, nó được thiết kế để tìm kiếm các từ khóa ở bất cứ chỗ nào trong chuỗi.
[266] Các cột nên đánh index:
[267] + Các cột thường xuất hiện trong điều kiện WHERE (phải tìm kiếm nhiều)
[268] + Cột dùng trong JOIN như các cột khóa chính hoặc khóa ngoại, thường khi tạo bảng thì khóa chính đã được đánh sẵn index (MySQL, PostgreSQL, Oracle,…)
[269] + Cột dùng ORDER BY, GROUP BY
[270] + Những cột có quá ít giá trị phân biệt (như giới tính chỉ có Nam/Nữ, trạng thái...), và những cột thường xuyên bị cập nhật hoặc ghi xóa thì không nên đánh index (index sẽ làm chậm thao tác cập nhật hoặc xóa)

[281] Query optimization
[282] Khi bạn gửi một truy vấn SQL, hệ quản trị cơ sở dữ liệu sẽ phân tích, chọn phương án thực hiện tối ưu (query plan).
[283] Query optimizer sẽ cân nhắc nhiều cách truy xuất dữ liệu khác nhau (dùng chỉ mục nào, JOIN kiểu gì,…).
[284] Các cách tối ưu hóa truy vấn thường dùng:
[285] Tạo index phù hợp trên cột dùng trong WHERE, JOIN, ORDER BY
[286] Tránh SELECT *
[287] Tránh dùng subquery khi có thể, các truy vấn lồng khiến CSDL phải thực hiện nhiều truy vấn lặp lại.
[288] -- Truy vấn lồng không cần thiết
[289] SELECT * FROM DonHang
[290] WHERE MaKhachHang IN
[291] (SELECT MaKhachHang FROM KhachHang WHERE TinhTrang = 'Active');
[293] -- Tối ưu hơn (dùng JOIN)
[294] SELECT d.* FROM DonHang d
[295] JOIN KhachHang k ON d.MaKhachHang = k.MaKhachHang
[296] WHERE k.TinhTrang = 'Active';
[298] Sử dụng EXISTS thay vì IN với truy vấn con lớn
[299] Sử dụng IN với subquery sẽ lấy toàn bộ kết quả subquery rồi mới so sánh từng giá trị, nếu subquery trả về nhiều dòng sẽ rất tốn bộ nhớ.
[300] EXISTS chỉ cần biết có tồn tại dòng nào thỏa mãn điều kiện là trả về ngay, thường nhanh hơn khi subquery lớn.
[301] -- Không tối ưu với subquery lớn
[302] SELECT * FROM DonHang
[303] WHERE MaKhachHang IN
[304] (SELECT MaKhachHang FROM KhachHang WHERE TinhTrang = 'Active');
[306] -- Tối ưu hơn
[307] SELECT * FROM DonHang d
[308] WHERE EXISTS (
[309] SELECT 1 FROM KhachHang k
[310] WHERE k.MaKhachHang = d.MaKhachHang AND k.TinhTrang = 'Active'
[311] );

[347] Transaction, Isolation Levels, Locking
[348] Transaction
[349] Là một tập hợp các thao tác (câu lệnh) với cơ sở dữ liệu, được thực hiện như một đơn vị duy nhất. Sau khi kết thúc transaction, mọi thay đổi đều được xác nhận (commit) hoặc hủy bỏ (rollback).
[350] ACID:
[351] A - Atomicity (Tính nguyên tử):
[352] Giao dịch hoặc là thực hiện toàn bộ, hoặc không thực hiện gì cả.
[353] C - Consistency (Tính nhất quán):
Sau mỗi transaction, hệ thống luôn ở trạng thái hợp lệ, không vi phạm các ràng buộc (ví dụ: không âm tiền, không trùng khóa, dữ liệu đúng logic nghiệp vụ).
[354] I - Isolation (Tính cô lập):
Các transaction đồng thời không gây ảnh hưởng lẫn nhau.
[355] Các thay đổi của transaction này không bị transaction khác nhìn thấy cho đến khi hoàn tất (commit). Giao dịch chạy như thể chúng thực hiện tuần tự.
[356] Ví dụ: A chuyển 1$ cho C, B cũng chuyển 1$ cho C cùng lúc. Nhờ isolation, C sẽ nhận đủ 2$ chứ không phải 1$.
[357] D - Durability (Tính bền vững):
Khi transaction được xác nhận (commit), thay đổi sẽ được lưu vĩnh viễn, không bị mất kể cả khi hệ thống bị sự cố (mất điện, crash server)
[358] Isolation Levels
[359] Isolation level là mức độ “cô lập” giữa các transaction.
[360] Read Uncommitted:
Transaction có thể đọc dữ liệu chưa xác nhận của transaction khác (dễ gây “dirty read” – đọc dữ liệu ảo, không thực tế).
[361] Read Committed:
Chỉ đọc được dữ liệu đã xác nhận (commit). Tránh dirty read, nhưng vẫn có thể gặp “non-repeatable read” (giá trị thay đổi giữa các lần đọc trong cùng transaction).
[362] Repeatable Read:
Trong suốt transaction, dữ liệu đã đọc sẽ không thay đổi, dù transaction khác có update. Tránh non-repeatable read, nhưng vẫn có thể bị “phantom read” (xuất hiện hoặc mất dòng khi insert/delete).
[363] Serializable:
Mức cao nhất, các transaction chạy tuần tự tuyệt đối. Đảm bảo an toàn nhưng hiệu năng thấp, dễ bị “wait” khi nhiều người cùng thao tác.
[365] Isolation level của các hệ quản trị CSDL:
[366] PostgreSQL: mặc định là Read Committed.
[367] MySQL InnoDB: mặc định là Repeatable Read.
[368] SQL Server: mặc định là Read Committed.
[369] Oracle: mặc định là Read Committed.
[371] Để setup isolation level, ví dụ trong Spring Boot với PostgreSQL:
[372] Spring Boot hỗ trợ annotation @Transactional với tham số isolation.
[374] Có thể cấu hình trong application.properties/application.yml (Spring Data JPA).
[375] spring.datasource.hikari.transaction-isolation=TRANSACTION_READ_COMMITTED
[377] Đặt isolation level trong truy vấn SQL thuần
[379] Ví dụ tổng hợp về ACID và Isolation
[380] Giả sử bạn chuyển 1$ từ tài khoản A sang tài khoản B:
[381] Bước 1: Trừ 1$ ở tài khoản A
[382] (Bước 1.5)
[383] Bước 2: Cộng 1$ vào tài khoản B
[384] Bước 3: Thực hiện commit giao dịch
[385] Tính nguyên tử (Atomicity): Nếu sau bước 1 (hoặc bước 1.5), hệ thống bị sự cố (crash), toàn bộ giao dịch sẽ bị hủy bỏ, không có thay đổi nào được lưu lại.
Thực tế: Sử dụng annotation @Transactional trong Spring Boot để đảm bảo tính nguyên tử.
[386] Tính nhất quán (Consistency): Sau bước 3 (commit), tổng số tiền trong hệ thống vẫn đúng, không tài khoản nào bị sai quy tắc (ví dụ: số dư âm).
Thực tế: Đảm bảo bằng các ràng buộc trong cơ sở dữ liệu như: khóa chính (PK), khóa ngoại (FK), unique, not null, check (điều kiện), default (giá trị mặc định).
[387] Tính cô lập (Isolation): Trong bước 1.5, các tài khoản khác không thể nhìn thấy việc A đã bị trừ 1$ mà B chưa được cộng 1$ (mức Read Commited trở lên).
Các mức độ isolation:
[388] + Read Uncommitted: Trong bước 1.5, tài khoản khác CÓ THỂ thấy A bị trừ 1$ nhưng b chưa được công 1$, là mức thấp nhất, không an toàn (gọi là “dirty read”).
[389] + Read Committed: Tài khoản khác chỉ nhìn thấy B được cộng 1$ sau khi commit (bước 3). Tránh được “dirty read” nhưng vẫn có thể bị “non-repeatable read” nếu kiểm tra nhiều lần trong một transaction.
[390] + Repeatable Read: Nếu một tài khoản khác kiểm tra số dư của B nhiều lần trong transaction (trong bước 1.5), số dư của B vẫn giữ nguyên (chưa được cộng 1$) suốt transaction đó.
[391] + Serializable: Chỉ một người có thể chuyển tiền vào B tại một thời điểm, người khác phải đợi cho đến khi giao dịch kết thúc. Đây là mức độ an toàn tuyệt đối, nhưng chậm hơn.
[392] Tính bền vững (Durability): Một khi hệ thống thông báo “chuyển tiền thành công”, kể cả khi mất điện hay có sự cố hệ thống, dữ liệu về giao dịch vẫn được lưu lại. Hoặc giả sử mất điện trước commit, transaction chưa commit sẽ bị rollback khi hệ thống khởi động lại. Dữ liệu trả về trạng thái cũ, giao dịch không có hiệu lực.
[394] Locking & Deadlock
[395] Locking (Khóa):
Là cơ chế đảm bảo dữ liệu không bị thay đổi đồng thời gây lỗi hoặc không nhất quán.
[396] + Pessimistic Locking (Khóa bi quan):
Đọc hoặc ghi dữ liệu đều đặt lock. Đọc thì dùng Shared Lock (nhiều người có thể đọc), ghi thì dùng Exclusive Lock (chỉ một người được ghi, người khác phải đợi). Đảm bảo an toàn nhưng dễ gây deadlock (kẹt nhau chờ lock) và giảm hiệu năng.
[397] + Optimistic Locking (Khóa lạc quan):
Không đặt lock khi đọc, chỉ kiểm tra khi ghi. Khi ghi, nếu dữ liệu đã bị ai đó thay đổi, thì sẽ báo lỗi hoặc rollback. Phù hợp hệ thống ít xung đột, dùng với @Version trong Spring Boot.
[398] Deadlock (Bế tắc):
Là trạng thái hai hoặc nhiều transaction cùng chờ nhau giải phóng lock, không transaction nào tiếp tục được.
[399] Ví dụ thực tế:
[400] Giả sử hệ thống có hai bảng:
[401] tb_sys_common_code
[402] tb_sys_translation
[403] Hai transaction đồng thời thực hiện:
[404] Transaction 1:
[405] Lock bản ghi A ở bảng tb_sys_common_code
[406] Đợi lock bản ghi B ở bảng tb_sys_translation
[407] Transaction 2:
[408] Lock bản ghi B ở bảng tb_sys_translation
[409] Đợi lock bản ghi A ở bảng tb_sys_common_code
[410] Cả hai transaction đều giữ lock mà bên kia cần, dẫn đến deadlock.
[411] Xử lý deadlock:
[412] Hệ quản trị như PostgreSQL, MySQL sẽ tự động phát hiện deadlock.
[413] Khi phát hiện deadlock, hệ thống sẽ rollback một trong các transaction liên quan và trả về lỗi để giải phóng các lock bị kẹt.
[414] Trong ứng dụng, developer cần bắt lỗi deadlock (ví dụ với Spring là DeadlockLoserDataAccessException) và xử lý retry transaction nếu cần.
[416] Tránh deadlock:
[417] Thiết kế thứ tự truy cập tài nguyên: Luôn truy cập các bảng/tài nguyên theo thứ tự cố định trong tất cả transaction.
[418] Giới hạn phạm vi lock: Chỉ lock những bản ghi thực sự cần thiết, tránh lock diện rộng.
[419] Đặt timeout cho các transaction: Nếu không lấy được lock sau một thời gian, transaction sẽ tự động rollback.
[420] Bắt và retry khi gặp deadlock: Ứng dụng nên xử lý retry transaction nếu gặp lỗi deadlock.
[421] Chọn isolation level phù hợp: Nếu hệ thống ít xung đột, sử dụng isolation level thấp hơn để giảm khả năng deadlock.
[423] Partitioning & Sharding, Replication & High Availability, Data Migration
[424] Partitioning & Sharding
[425] Partitioning là chia một bảng to thành nhiều “miếng nhỏ” theo tiêu chí nào đó (ví dụ chia theo năm, theo vùng miền, theo loại dữ liệu).
[426] Ví dụ partition bảng theo năm, khi cần lấy dữ liệu năm 2023, database chỉ đọc đúng phần đó thay vì cả bảng → truy vấn chạy nhanh hơn nhiều.
[427] Sharding thì giống chia thành nhiều “database con” ở các server khác nhau, mỗi nơi lưu một phần dữ liệu.
[428] Ví dụ shard theo vùng miền, user ở miền Bắc chỉ đọc database miền Bắc, user miền Nam đọc database miền Nam → tải chia đều, hệ thống không quá tải.
[429] Replication & High Availability
[430] Replication là việc sao chép dữ liệu từ một máy chính sang một hoặc nhiều máy phụ. Máy phụ chỉ để đọc, máy chính vừa đọc vừa ghi.
[431] High Availability là thiết kế hệ thống để luôn hoạt động liên tục, giảm tối đa nguy cơ bị downtime, kể cả khi có sự cố hoặc máy chủ bị hỏng.
[432] + Failover là cơ chế tự động chuyển sang hệ thống dự phòng nếu hệ thống (node) chính bị lỗi.
[433] + Load Balancing là việc phân phối các request tới nhiều server để tăng hiệu năng và tránh quá tải.
[434] Ví dụ Khi có hàng nghìn truy vấn SELECT, hệ thống sẽ chia đều các truy vấn này tới nhiều database replica để xử lý song song, giúp hệ thống chạy nhanh và ổn định.

[437] SQL truyền thống (chạy trên một node hoặc cluster nhỏ) thường ưu tiên CA -  Consistency và Availability. Trong trường hợp SQL phân tán, vẫn phải ưu tiên Partition Tolerance trước.

[505] Scenario
[506] Dùng JPA khác gì dùng Native Query?
[507] Ngôn ngữ truy vấn
[508] JPA (JPQL/Criteria): Dùng truy vấn dựa trên entity, không phụ thuộc vào cấu trúc bảng thật.
[509] Native Query: Dùng SQL thuần của database, phụ thuộc vào từng loại DB.
[510] Tính di động
[511] JPA: Dễ chuyển đổi giữa các DBMS khác nhau.
[512] Native Query: Có thể lỗi khi đổi DBMS do khác cú pháp SQL.
[513] Tính an toàn & kiểm tra lỗi
[514] JPA: Kiểm tra cú pháp khi biên dịch, thuận tiện refactor.
[515] Native Query: Chỉ kiểm tra ở runtime, dễ sai tên trường/cột.
[516] Tính năng nâng cao
[517] JPA: Hỗ trợ ORM, lazy loading, cache, mapping,...
[518] Native Query: Không hỗ trợ ORM trực tiếp, cần tự ánh xạ kết quả.
[519] Hiệu năng & tối ưu
[520] JPA: Phù hợp truy vấn thông thường.
[521] Native Query: Tối ưu mạnh cho truy vấn phức tạp, đặc thù DB.
[522] Nên dùng Native Query khi:
[523] Cần các tính năng SQL mà JPQL không hỗ trợ.
[524] Truy vấn lớn, report phức tạp, hoặc stored procedure.
[526] Một số tình huống tối ưu DB trong thực tế
[527] Tình huống: Truy vấn tìm kiếm chậm do thiếu index
[528] Mô tả: Bảng orders có hàng triệu bản ghi. Khi truy vấn lọc theo trường customer_id, tốc độ rất chậm.
[529] Giải pháp:
[530] Tạo index cho trường customer_id:
[531] CREATE INDEX idx_customer_id ON orders(customer_id);
[532] Sau khi có index, truy vấn như SELECT * FROM orders WHERE customer_id = ? sẽ nhanh hơn nhiều.
[533] Tình huống: Gặp vấn đề N+1 Query khi lấy danh sách User cùng danh sách Address của họ.
[534] Mô tả: Sử dụng JPA, khi lấy danh sách User và địa chỉ (OneToMany), mỗi User lại sinh thêm 1 query để lấy Address → tổng số query = N+1, rất kém hiệu năng.
[535] Giải pháp:
[536] Sử dụng fetch join trong JPQL:
[537] @Query("SELECT u FROM User u LEFT JOIN FETCH u.addresses")
List<User> findAllWithAddresses();
[538] Như vậy chỉ cần 1 query để lấy toàn bộ User cùng Address.
[539] Ngoài ra còn cách dùng @EntityGrapth:
[540] public interface UserRepository extends JpaRepository<User, Long> {
[541] @EntityGraph(attributePaths = "addresses")
[542] @Query("SELECT u FROM User u")
[543] List<User> findAllWithAddresses();
[544] }
[545] Entity Graph sẽ chỉ dẫn JPA/Hibernate lấy cả addresses khi truy vấn danh sách user, do đó chỉ sinh ra 1 hoặc 2 query, tránh N+1.
[546] Dùng @BatchSize:
[547] @Entity public class User {
[548] @Id
[549] private Long id;
[550] private String name;
[552] @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
[553] @BatchSize(size = 10)
[554] private List<Address> addresses;
[555] }
[556] hoặc
[557] spring.jpa.properties.hibernate.default_batch_fetch_size=20
[558] Với batch size, khi truy cập getAddresses() của nhiều user, Hibernate sẽ gom các truy vấn lại và lấy dữ liệu theo batch, giảm số lượng query so với từng user một.
[559] Giảm N+1 truy vấn xuống còn 1 + ceil(N / batch_size)
[561] Tình huống: Truy vấn report tổng hợp, tính toán chậm
[562] Mô tả: Cần tính tổng số lượng bán ra theo từng sản phẩm trong tháng, dữ liệu lớn, join nhiều bảng.
[563] Giải pháp:
[564] Viết native query với các hàm tổng hợp, tận dụng index, hoặc tạo view/stored procedure trong DB:
[565] SELECT product_id, SUM(quantity) as total_sold
FROM order_details
WHERE order_date BETWEEN ? AND ?
GROUP BY product_id;
[566] Tạo view nếu report thường xuyên dùng:
[567] CREATE VIEW product_sales_monthly AS
SELECT product_id, EXTRACT(YEAR_MONTH FROM order_date) as ym, SUM(quantity) as total_sold
FROM order_details
GROUP BY product_id, ym;
[569] Tình huống: Insert/Update hàng loạt gây chậm
[570] Mô tả: Cần insert/update hàng nghìn bản ghi, mỗi bản ghi lại thực hiện 1 lần insert/update riêng.
[571] Giải pháp:
[572] Sử dụng batch insert/update:
[573] for (int i = 0; i < list.size(); i++) {
    entityManager.persist(list.get(i));
    if (i % batchSize == 0) {
        entityManager.flush();
        entityManager.clear();
    }
}
[574] Kết hợp cấu hình batch_size trong application.properties khi dùng Hibernate:
[575] spring.jpa.properties.hibernate.jdbc.batch_size=50
[577] Tình huống: Truy vấn phân trang (paging) không hiệu quả khi OFFSET quá lớn.
[578] Mô tả: Khi phân trang dữ liệu lớn, OFFSET càng lớn thì truy vấn càng chậm (ví dụ OFFSET 100000). Ví dụ không nên truy vấn như sau:
[579] SELECT id, order_date FROM orders ORDER BY id LIMIT 100 OFFSET 100000;
[580] Giải pháp:
[581] Sử dụng keyset pagination (dựa trên giá trị field như id):
[582] SELECT id, order_date FROM orders WHERE id > ? ORDER BY id LIMIT 100;
[583] Tránh dùng OFFSET trực tiếp khi dữ liệu lớn.
[584] Tình huống: Dữ liệu truy vấn lặp đi lặp lại nhiều lần (hot data)
[585] Mô tả: Một số truy vấn đọc dữ liệu giống nhau liên tục, gây áp lực lên DB.
[586] Giải pháp: Sử dụng cache (Redis, Memcached, hoặc cache của Hibernate):
[587] Cache kết quả truy vấn ở tầng ứng dụng.
[588] Dùng Hibernate 2nd Level Cache nếu phù hợp.

[599] Sự khác nhau Abstract Class và Interface?
[600] Abstract Class:
[601] Có thể có những method có thân hàm
[602] Có constructor, biến instance
[603] Đơn kế thừa, một class chỉ extends được một class cha

[609] AC sử dụng khi muốn chia sẻ logic code chung. Ví dụ Dog, Cat extend từ lớp abstract Animal, có thể có những đặc điểm chung như tên hoặc method eat(), nhưng ngoài ra cũng có những method abstract như makeSound() để có thể cài đặt riêng.
[610] Interface sử dụng khi cần định nghĩa một bản hợp đồng hành vi. Đó là khi ta muốn các class khác nhau nhưng vẫn phải có chung một hành vi, chức năng

[641] Collections
[642] Overview
[643] Collection Framework là tập hợp các class và interface hỗ trợ thao tác với tập dữ liệu ĐỘNG (List, Set, Map, Queue), nó khác với Arrays (có kích thước cố định) và cung cấp nhiều thuật toán như sort, search, shuffle
[644] Collection là INTERFACE, Collections là CLASS tiện ích
[645] Iterator: dùng để duyệt 1 CHIỀU các phần tử của Collection, chỉ có next(), hasNext(), remove()
[646] ListIterator: nâng cấp của Iterator, chỉ dùng cho List, duyệt 2 chiều, có cả next và previous, hỗ trợ thêm sửa xóa phần tử trong khi duyệt
[647] Tại sao Collection là interface gốc thay vì Class?
[648] Để cho phép nhiều cấu trúc dữ liệu khác nhau (ArrayList, HashSet, LinkedList) implement linh hoạt.
[649] fail-fast iterator: ném ConcurrentModificationException nếu collection bị thay đổi cấu trúc khi đang duyệt
[650] Ví dụ ArrayList, HashMap
[651] fail-safe iterator: cho phép duyệt mà không lỗi, nhưng có thể không thấy cập nhật mới
[652] Ví dụ ConcurrentHashMap, CopyOnWriteArrayList
[653] Collection (lưu trữ theo phần tử rời rạc)
[654] List: có thứ tự, cho phép phần tử trùng lặp (cả kể null)
[655] + ArrayList: truy cập theo chỉ số, thêm và xóa cuối nhanh O(1), xóa index O(n), thích hợp cho đọc nhiều (truy cập theo chỉ số, O(1))
[656] + LinkedList: linked list trong Java là double-linked list (2 chiều)
[657] Thao tác thêm/xóa ở đầu/cuối nhanh, truy cập ngẫu nhiên chậm (do phải duyệt từ đầu hoặc cuối O(n)), thích hợp lưu dữ liệu thao tác thêm/xóa nhiều
[658] Đa năng, có thể dùng như List, Queue, Deque, Stack
[659] + Vector/Stack: cũ, ít dùng; Vector thread-safe, Stack LIFO
[660] Set: không cho phép phần tử trùng lặp, thường không thứ tự (LinkHashSet, TreeSet có thể có thứ tự)
[661] + HashSet: không thứ tự, không trùng lặp, thao tác nhanh
[662] Dựa trên HashMap - chỉ lưu key, value là dummy object
[663] Check 2 phần tử bằng nhau: so sánh hashCode() trước, sau đó equals()
[664] + LinkedHashSet: giữ thứ tự thêm, không trùng lặp
[665] + TreeSet: sắp xếp tự nhiên hoặc theo Comparator/Comparable, thích hợp khi cần duyệt có thứ tự, không cho phép null (vì không so sánh được)
[666] Queue/Deque (Double end queue): Lưu trữ theo hàng đợi, FIFO hoặc LIFO, cho phép trùng lặp
[667] + PriorityQueue: hàng đợi ưu tiên theo Comparator/Comparable, không cho phép null, nếu 2 phần tử cùng độ ưu tiên thì không đảm bảo thứ tự ổn định
[668] + ArrayDeque: hàng đợi 2 đầu, không giới hạn kích thước, thao tác đầu cuối đều nhanh O(1), không cho phép null

[695] synchronized và volatile
[696] synchronized: khóa đối tượng hoặc method, đảm bảo chỉ có 1 thread truy cập được vào vùng code đó tại một thời điểm.
[697] synchronized method khóa toàn bộ method, sychronized block chỉ khóa một đoạn code nhỏ nên hiệu năng tốt hơn
[698] volatile: dùng cho biến, đảm bảo khi 1 thread thay đổi giá trị của biến đó, các thread sẽ ngay lập tức nhìn thấy giá trị mới đó
[699] volatile chỉ đảm bảo visibility, synchronized đảm bảo cả visibility và mutual exclusion (không có race condition) / cả khối code đó là atomicity
[700] Tức, đối với thao tác nguyên tử, chỉ có 1 bước duy nhất (như thay đổi status từ true thành false) chỉ cần dùng volatile để đảm bảo thêm visibility.
[701] Đối với thao tác gồm nhiều bước (một luồng khác có thể chen vào trong khi đang thực thi), ví dụ counter++ (gồm 3 bước đọc, tăng, ghi). Nếu chỉ dùng volatile, 2 thread có thể cùng đọc giá trị cũ, dẫn đến race condition. Khi đó dùng synchronized, đảm bảo cả tính atomicity của chuỗi thao tác trên.
[702] volatile phù hợp với biến có thao tác nguyên tử - boolean, flag, status...
[703] synchronize dùng với các thao tác phức tạp hơn như tăng biến số nguyên
[704] wait(), notify(), notifyAll()
[705] Phải gọi trong khối synchronized (thread phải giữ lock của object đó)
[706] wait() làm thread hiện tại dừng lại để chờ 1 thread khác gọi notify() hoặc notifyAll()
[707] notify() đánh thức một thread khác trên cùng 1 object, nếu có nhiều thread, đánh thức MỘT thread bất kì
[708] notifyAll(): đánh thức tất cả thread đang wait() trên cùng 1 object
[709] 3 method trên giải quết vấn đề phối hợp giữ nhiều thread khi truy cập hoặc thao tác trên các tài nguyên dùng chung

[729] Atomic Variables
[730] Là các biến đặc biệt được thiết kế hỗ trợ các thao tác đọc, ghi, tăng, giảm, cập nhật... một cách an toàn trong môi trường đa luồng mà không cần dùng synchronize. Nó biến các thao tác trên với biến trở nên duy nhất (atomicity), do đó tránh được race-condition.
[731] AtomicInteger, AtomicLong, AtomicBoolean...
[732] Hiệu năng cao hơn synchronized do dùng cơ chế CAS – compare and swap (một câu lệnh gốc CPU nên nhanh)
[733] Ví dụ khi thực hiện thao tác tăng trên một biến đang có giá trị 10, nếu dùng synchronized, phải khóa biến đó lại, cho luồng chính (được phép truy cập) tăng lên 11 rồi mới nhả khóa cho các luồng khác chạy tiếp, rất mất thời gian.
[734] Nếu dùng atomic variable, nó sẽ lưu lại giá trị ban đầu là 10. Giả sử trong lúc luồng chính đang tăng biến lên 11 mà có 1 luồng khác đã tăng nó lên 11 trước. CPU sẽ so sánh giá trị hiện tại (11) với giá trị ban đầu đã lưu (10). Do khác nhau nên nó sẽ cập nhật giá trị ban đầu thành 11 và tiếp tục quy trình trên.

[744] Deadlock & Livelock
[745] Deadlock: là hiện tượng xảy ra khi 2 hoặc nhiều luồng chờ lẫn nhau giải phóng tài nguyên dẫn đến tất cả bị treo vô thời hạn.
[746] Ví dụ có 2 object lock A và B. Luồng 1 lock A trước rồi cố lock B. Luồng 2 lock B trước rồi cố lock A. Cả 2 bị treo vì không chịu nhả tải nguyên.
[747] Cách phòng tránh:
[748] + Đảm bảo lock tài nguyên đúng thứ tự, ví dụ luôn lấy A rồi mới lấy B.
[749] + Dùng tryLock() của lớp ReentranLock thay vì lock với synchronized.
[750] tryLock(): luồng không bị chặn, thay vì chờ khóa mãi như synchronized, tryLock() chỉ thử lấy khóa, nếu không lấy được, giải phóng các tài nguyên đã giữ và thử lại hoặc xử lý logic khác.
[751] + Sử dụng tryLock(long timeout, TimeUnit unit) set timeout để đặt thời gian giữ lock của một luồng, tránh bị lock vô thời hạn.
[752] + Hạn chế lock nhiều tài nguyên đồng thời
[753] Livelock: các thread vẫn chạy và thay đổi trạng thái, nhưng công việc không tiến triển. Hiếm gặp hơn deadlock.
[754] Ví dụ mình và ny mình cùng ăn tối nhưng chỉ có 1 chiếc thìa. Mình cầm thìa chuẩn bị ăn nhưng mình biết ny mình đói nên nhường thìa cho ẻm, ẻm cầm thìa xong lại nghĩ mình đói nên lại nhường thìa cho mình. Cuối cùng cả hai cùng đói mà không thực hiện được việc ăn.

[998] AOP – Aspect Oriented Programming
[999] AOP là kĩ thuật lập trình hướng khía cạnh, giúp tách các phần logic phụ trợ ra khỏi code chính, giúp các method tập trung vào business logic. Các logic phụ trợ thường gặp là logging, quản lý transaction, kiểm tra quyền (lúc truy cập vào method)...
[1000] AOP không thay thế OOP mà nó bổ trợ cho OOP. Ví dụ OOP đáng lẽ nên tập trung vào logic nghiệp vụ chính thì lại có những đoạn logic không liên quan như ghi log, kiểm tra quyền..., và điều này khiến code lặp lại ở nhiều nơi. AOP giúp tách biệt hoàn toàn các logic này ra khỏi các class business chính.
[1001] Các thành trong AOP:
[1002] + Aspect: nơi chứa logic phụ trợ (ví dụ logging logic)
[1003] + Advice (Lời khuyên/hành động): Đoạn code sẽ thực thi ở một điểm cụ thể (trước, sau, quanh method)
[1004] Ví dụ trước khi bất cứ hàm nào trong service chạy, hãy in: ‘Bắt đầu method!’
→ Đoạn code System.out.println(“Bắt đầu method!”); là advice.
[1005] + Join Point (Điểm kết nối): Là điểm cụ thể trong quá trình thực thi chương trình, nơi advice có thể được áp dụng (thường là khi gọi method).
[1006] Ví dụ khi bạn gọi userService.login() hoặc orderService.createOrder(), mỗi lần gọi method này là một join point.
[1007] + Pointcut (Điểm cắt): Điều kiện/biểu thức xác định những join point nào sẽ áp dụng advice (chọn những method nào để “gắn” advice).
[1008] Bạn muốn ghi log cho mọi method trong package service:
→ Pointcut là: execution(* com.example.service.*.*(..))
[1009] + Weaving (Kết hợp): Quá trình “gắn” aspect vào đúng chỗ trong code (các join point) khi ứng dụng chạy, biên dịch hoặc load class.
[1010] Khi bạn chạy app, Spring hoặc AspectJ sẽ tự động “chèn” code log của bạn vào đúng các method đã định nghĩa trong pointcut.

[1132] List<T>: chỉ trả về danh sách kết quả, không hỗ trợ thông tin phân trang.
[1133] Tuỳ yêu cầu mà tôi sẽ chọn kiểu trả về phù hợp. Nếu cần hiển thị tổng số trang, số bản ghi thì sẽ chọn Page<T>;. Nếu chỉ cần biết có trang tiếp theo hay không thì dùng Slice<T>;. Nếu không cần phân trang thì chỉ trả về List<T>.
[1134] DTO Projection
[1135] DTO projection là kỹ thuật truy vấn dữ liệu từ database và trả về một lớp trung gian gọi là DTO (Data Transfer Object) thay vì trả về trực tiếp entity (đối tượng ánh xạ với bảng trong DB).
[1136] Giúp tối ưu hiệu năng, bảo mật, tách biệt logic và tránh lỗi LazyInitialization Exception.
[1137] Constructor Expression (SELECT new ...)
[1138] Dùng JPQL với HQL với cú pháp SELECT new.
[1139] Ví dụ có entity User với nhiều trường, nhưng chỉ cần trả về id và name.
[1141] Dùng khi cần DTO có logic, nhiều trường phức tạp.
[1142] Interface-based Projection
[1143] Chỉ cần định nghĩa một interface (không cần viết class), có các phương thức getter trùng với tên trường cần lấy.
Spring Data JPA sẽ tự động map dữ liệu entity vào interface này.
[1146] Dùng khi truy vấn đơn giản, lấy vài trường.
[1147] LazyInitializationException:
[1148] Entity Relationships
[1149] Ánh xạ các quan hệ: OneToMany, ManyToOne, OneToOne, ManyToMany
[1151] FetchType:
[1152] + EAGER (Mặc định cho @ManyToOne, @OneToOne):
[1153] Khi truy vấn entity cha, các entity con liên quan sẽ được load cùng lúc (tức là luôn JOIN hoặc query ngay lập tức).
[1154] + LAZY (Mặc định cho @OneToMany, @ManyToMany):
[1155] Khi truy vấn entity cha, các entity con liên quan chỉ được load khi truy cập đến (tức là sẽ sinh truy vấn riêng khi gọi getter).
[1156] Chỉ nên dùng EAGER nếu thực sự luôn cần dữ liệu con mỗi khi lấy cha (tránh sinh ra JOIN lớn, hoặc tải dư dữ liệu).
[1157] Thường để mặc định LAZY, khi thực sự cần mới lấy (giảm tải, tăng hiệu năng).
[1158] N+1 problem:
[1159] Khi lấy danh sách cha (ví dụ, 100 User), sau đó truy cập đến danh sách con (addresses của từng user), JPA sẽ lặp lại truy vấn con với mỗi cha, gây ra N+1 truy vấn.
[1160] Giải pháp:
[1161] + Fetch Join:
[1162] @Query("SELECT u FROM User u LEFT JOIN FETCH u.addresses")
List<User> findAllWithAddresses();
[1163] Như vậy chỉ cần 1 query để lấy toàn bộ User cùng Address.
[1164] + Dùng @EntityGraph:
[1165] public interface UserRepository extends JpaRepository<User, Long> {
[1166] @EntityGraph(attributePaths = "addresses")
[1167] @Query("SELECT u FROM User u")
[1168] List<User> findAllWithAddresses();
[1169] }
[1170] Entity Graph sẽ chỉ dẫn JPA/Hibernate lấy cả addresses khi truy vấn danh sách user, do đó chỉ sinh ra 1 hoặc 2 query, tránh N+1.
[1171] + Dùng @BatchSize:
[1172] @Entity public class User {
[1173] @Id
[1174] private Long id;
[1175] private String name;
[1177] @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
[1178] @BatchSize(size = 10)
[1179] private List<Address> addresses;
[1180] }
[1181] hoặc
[1182] spring.jpa.properties.hibernate.default_batch_fetch_size=20
[1183] Với batch size, khi truy cập getAddresses() của nhiều user, Hibernate sẽ gom các truy vấn lại và lấy dữ liệu theo batch, giảm số lượng query so với từng user một.
[1184] Giảm N+1 truy vấn xuống còn 1 + ceil(N / batch_size)

[1186] Transaction
[1187] Khi một phương thức được đánh dấu @Transactional, toàn bộ các thao tác database bên trong sẽ được thực hiện trong một transaction duy nhất.
[1188] Nếu có exception (lỗi), transaction sẽ rollback (hoàn tác). Nếu thành công, transaction sẽ commit (lưu vào DB).
[1190] Spring sử dụng AOP (Aspect-Oriented Programming) để tự động mở/đóng transaction xung quanh các phương thức được đánh dấu @Transactional.
[1191] Một số lưu ý:
[1192] + Scope:
Đặt @Transactional ở service layer (class hoặc method), không nên đặt ở repository.
[1193] + Propagation:
Mặc định là REQUIRED (nếu đang có transaction thì dùng chung, chưa có thì tạo mới).
[1194] + Rollback:
Mặc định rollback khi gặp RuntimeException hoặc Error, không rollback với checked exception trừ khi cấu hình thêm.
[1195] + ReadOnly:
Có thể dùng @Transactional(readOnly = true) cho các method chỉ đọc để tối ưu hiệu năng.

[1239] Cấu hình cơ bản
[1241] JWT (JSON Web Token)
[1242] Là token được mã hóa từ một JSON object, dùng trong xác thực stateless giữa client và server.
[1243] Cấu trúc: gồm 3 phần, ngăn cách bởi dấu chấm
[1244] + Header: thông tin loại token và loại thuật toán được sử dụng cho sử dụng như HS256 và RS256
[1245] + Payload: chứa thông tin user và token như userId, roles, thời gian hết hạn... không nên lưu các thông tin nhạy cảm ở Payload.
[1246] + Signature: được mã hóa bằng Header + Payload và một secret key chỉ server mới biết. Do đó dù Header và Payload được mã hóa Base64, tức là nếu có token, có thể giải mã ngược và thấy được thông tin Header và Payload, nhưng nếu thay đổi chúng, signature không đồng nhất, secret key ở server sẽ không thể xác thực và token trở nên không hợp lệ.
[1247] Ưu điểm:
[1248] Đối với các web application sử dụng phương thức xác thực truyền thống qua cookie/session lưu ở trên server, client sẽ phải luôn gọi đúng về server đó để xác thực. Giả sử ứng dụng của chúng ta cần mở rộng thêm nhiều server hoặc triển khai microservices, client sẽ không biết gọi về server nào để xác thực, điều này có thể được giải quyết bằng sticky session (gắn 1 client với 1 server) nhưng nhược điểm vẫn kém rất nhiều trong việc dùng JWT trong trường hợp này.
[1249] Việc dùng JWT khiến cho ứng dụng stateless thực sự, tức là không cần lưu bất kì user session nào trên server, chỉ cần lưu token trên client và gửi kèm thông tin xác thực trong mỗi request. Nó cũng giúp khả năng mở rộng, auto-scaling, tích hợp đa vùng tốt hơn. Rất phù hợp cho các hệ thống phân tán, microservices, yêu cầu mở rộng linh hoạt, high availability.
[1250] Nhược điểm: Tuy nhiên cũng có một nhược điểm lớn đó là một khi đã phát hành token cho client, nó sẽ hợp lệ đến khi hết hạn, dù người dùng có đăng xuất hay bị khóa. Dẫn đến rủi ro bảo mật nếu lộ token.
[1251] Các ứng dụng lớn hiện nay thường kết hợp dùng access token và refresh token để giải quyết phần nào bài toán trên. Khi người dùng đăng nhập thành công, hệ thống sẽ trả về access token và refresh token. Access token để đính kèm header trong mỗi request người dùng phục vụ việc xác thực, còn refresh token để lấy access token mới khi nó hết hạn.
[1252] + Access token được đặt thời hạn ngắn khoảng 5 - 15 phút, nên lưu trên localStorage.
[1253] + Refresh token có thời hạn dài hơn, thường là 7 – 30 ngày, nên lưu trên Cookie được gắn cờ Http Only hoặc trên Redis (với hệ thống phân tán)
[1255] Do access token có thời gian sống ngắn, nên nếu bị lộ access token cũng giảm thiểu thời gian khai thác hệ thống.
[1256] Với hệ thống cần bảo mật cao, muốn thu hồi token ngay lập tức khi đăng xuất có thể triển khai một Blacklist access token trên server (thường là trên Redis với hệ thống phân tán, phản hồi nhanh), mỗi lần API nhận request, kiểm tra access token đó có nằm trong blacklist không.
[1257] Ngoài ra các hệ thống đa nền tảng như Facebook, Google... hệ thống sẽ cấp riêng refresh token cho từng thiết bị để ví dụ đăng xuất trên máy tính nhưng trên điện thoại vẫn ở trạng thái đăng nhập. Hoặc khi mất điện thoại, nghi ngờ có thiết bị lạ vào tài khoản, có thể chọn đăng xuất khỏi tất cả các thiết bị.
[1258] Để cải thiện trải nghiệm người dùng, không phải đăng nhập lại khi hết hạn refresh token, mỗi lần làm mới access token, server đồng thời cấp luôn refresh token mới, nếu người dùng hoạt động thường xuyên, refresh token sẽ luôn được làm mới.
[1259] Cấu hình trong Spring Boot:
[1262] OAuth2
[1263] Là phương thức xác thực ủy quyền cho bên thứ ba ví dụ Google, Facebook mà không cần nhập user name, password.
[1264] Quy trình cơ bản:
[1265] Ứng dụng hỏi có đồng ý cấp quyền đăng nhập với Google, Facebook không.
[1266] Nếu đồng ý, dịch vụ bên thứ ba sẽ cấp cấp cho ứng dụng một access token dùng để gọi API từ ứng dụng.
[1267] Access token có thời gian sử dụng ngắn, khi hết hạn sẽ dùng refresh token để lấy một access token mới.
[1268] Như vậy, thay vì ứng dụng gửi token cho client, dịch vụ bên thứ 3 sẽ được ủy quyền làm việc đó, thường dùng JWT làm chuẩn token xác thực
[1269] Cấu hình OAuth2 với Spring Boot:
[1270] Cần cấu hình thêm về issuer-uri, public key hoặc jwk-set-uri trong file application.properties.
[1271] Method-level security (@PreAuthorize, @Secured)
[1272] Để bật bảo mật method-level, sử dụng annotation sau trong class cấu hình bảo mật (có @Configuration):
[1273] @EnableMethodSecurity(prePostEnabled = true, securedEnabled = true)
[1274] + prePostEnabled = true:
Bật @PreAuthorize, @PostAuthorize.
[1275] + securedEnabled = true:
Bật @Secured.
[1276] Các annotation sử dụng cho method-level sucurity:
[1277] @PreAuthorize: Kiểm tra điều kiện quyền trước khi thực thi method. Có thể dùng Spring Expression Language (SpEL) để kiểm tra role, quyền, điều kiện...
[1278] @PostAuthorize: Kiểm tra điều kiện sau khi thực thi method.
[1279] @Secured: Chỉ kiểm tra role được truy cập method, không thể kiểm tra điều kiện phức tạp.
[1280] @RolesAllowed: Tương tự @Secured, dùng chuẩn Java EE. Ít dùng.
[1281] Ví dụ:
[1284] hasRole(‘ADMIN’) trong @PreAuthorize tự động hiểu là ROLE_ADMIN
[1285] Nếu sử dụng @Secured thì phải viết đầy đủ ROLE_ADMIN
[1286] Nên dùng method-level security khi cần bảo vệ nghiệp vụ ở tầng service, kiểm tra quyền phức tạp, hoặc đảm bảo mọi luồng truy cập đều phải qua kiểm tra bảo mật, không chỉ ở endpoint.
[1287] Trong các hệ thống microservice, các method nghiệp vụ có thể được gọi qua nhiều API khác nhau. Method-level security giúp bảo vệ chặt chẽ ở tầng nghiệp vụ, dù gọi từ đâu.
[1288] Tổng quan luồng xử lý
[1289] Request HTTP tới server ngay từ đầu sẽ gặp phải một chuỗi các filter của Spring Security gọi là Security Filter Chain.
[1290] Mỗi filter có một nhiệm vụ riêng như authentication, authorization, bảo vệ CSRF, xử lý đăng xuất...
[1291] Filter bảo vệ CSRF:
[1292] CSRF (Cross-Site Request Forgery) là tấn công dựa trên việc kẻ xấu lợi dụng trình duyệt của người dùng đã đăng nhập sẵn (có session/cookie) để thực hiện các hành động không mong muốn trên một website khác.
[1293] Với web application dùng session thì luôn nên bật bảo vệ CSRF.
[1294] Với REST API stateless dùng JWT, OAuth2, không dùng session: nếu token ở client được lưu vào localStorage/sessionStorage (như access token) và được đính kèm vào header Authorization trong mỗi request thì không cần bật bảo vệ CRSF. Nếu token ở client được lưu vào cookie (như refresh token) thì nên bật bảo vệ CSRF.
[1295] Xác thực (authentication):
[1296] Đầu tiên, hệ thống kiểm tra request đã được xác thực hay chưa.
[1297] Nếu chưa, các filter liên quan (như UsernamePasswordAuthenticationFilter đối với form login, hoặc một custom filter cho JWT) sẽ chịu trách nhiệm lấy thông tin xác thực từ request (username/password, token)
[1298] Thông tin này sẽ được kiểm tra thông qua AuthenticationManager và các AuthenticationProvider. Nếu xác thực thành công, thông tin người dùng được lưu vào SecurityContext
[1299] Phân quyền (authorization):
[1300] Sau khi xác thực, Spring Security tiếp tục kiểm tra quyền truy cập của user với endpoint đang gọi. Điều này dựa trên các rule cấu hình (ví dụ role, authority...)
[1301] Nếu không đủ quyền, hệ thống trả về lỗi 403 Forbidden.
[1302] Nếu cả xác thực và phân quyền đều hợp lệ, request sẽ được chuyển tới controller, service để xử lý logic nghiệp vụ
[1303] Các filter cuối cùng có thể xử lý thêm các vấn đề như logout, exception handling, hoặc ghi log nếu cần.

[1305] Luôn sử dụng các thuật toán mã hóa password mạnh như BCrypt
[1306] Kiểm soát CORS: Nếu ứng dụng là API phục vụ frontend khác domain (ví dụ frontend dùng cổng 3000, backend dùng cổng 8080), cần cấu hình CORS.
[1307] Custom Exception Handling:
[1308] Vấn đề của xử lý exception khi sử dụng Spring Security là nó chặn trước request trước khi nó có thể gọi đến lớp xử lý exception nếu xảy ra lỗi xác thực. Ví dụ người dùng gửi về một JWT không hợp lệ, nó sẽ không thể trả về một thông báo lỗi theo format mà lớp xử lý exception của hệ thống tạo ra.
[1309] Cách tốt nhất là sử dụng AuthenticationEntryPoint để trả về 401 (lỗi xác thực, token không hợp lệ) và AccessDeniedHandler để trả về 403 (không đủ quyền). Khi trả lỗi có thể tùy chỉnh cho giống format của lớp exception chung.

[1321] when(...).thenReturn(...): Định nghĩa hành vi cho mock. Khi gọi userRepository.findById(1), nó sẽ trả về một Optional&lt;User&gt; chứa đối tượng user.

[1328] @SpringBootTest: Khởi động toàn bộ Spring context (gần giống như chạy thật), inject các bean thật vào test.

[1333] Test Controller với @WebMvcTest

[1372] Spring Cloud
[1373] Service Discovery & Registry
Các service tự đăng ký địa chỉ của mình và phát hiện các service khác. Cho phép các service tự tìm nhau thay vì phải cấu hình địa chỉ cứng.
[1374] Ví dụ: Eureka, Zookeeper.
[1375] Trong Spring Cloud, Eureka là giải pháp service discovery mặc định và phổ biến nhất. Zookeeper cũng được hỗ trợ, nhưng chủ yếu dùng khi có nhu cầu hoặc yêu cầu đặc biệt từ hệ thống.
[1377] API Gateway
[1378] API Gateway là cổng vào duy nhất, nhận request từ client, kiểm tra, xác thực, log, rồi chuyển tiếp đến các service phù hợp phía sau.
[1379] Spring Cloud Gateway là giải pháp gateway hiện đại, non-blocking, hiệu năng cao của Spring Cloud.
Ngoài ra, nếu hệ thống cần gateway độc lập, đa nền tảng, có thể dùng Kong Gateway, nhưng trong hệ sinh thái Spring Cloud thì Spring Cloud Gateway là lựa chọn chính thống..
[1380] Configuration Management
[1381] Trong hệ thống microservices với Spring Cloud, Spring Cloud Config Server đóng vai trò là nơi lưu trữ và phân phối cấu hình tập trung (có thể lưu trong Git, file, hoặc database).
[1382] Các microservice sẽ cấu hình địa chỉ Config Server trong bootstrap.yml/properties. Khi khởi động, mỗi service sẽ tự động lấy cấu hình động từ Config Server về để sử dụng. Nếu muốn cập nhật cấu hình không cần restart, có thể gọi /actuator/refresh hoặc dùng Spring Cloud Bus để refresh tự động.
[1383] Load Balancing
[1384] Spring Cloud LoadBalancer giúp các request từ các service được phân phối đều đến các instance phía sau, tăng hiệu năng, tránh quá tải và giúp hệ thống microservices linh hoạt, dễ mở rộng.
[1385] Circuit Breaker & Resilience
[1386] Circuit breaker pattern là một mẫu thiết kế giúp bảo vệ hệ thống khi gọi đến các service bên ngoài (hoặc thành phần không ổn định).
[1387] Thường sử dụng Resilence4j.
Nếu phát hiện service bị lỗi liên tục (timeout, exception...), circuit breaker sẽ tạm “ngắt mạch” (cắt luồng), không gửi thêm request mới trong một thời gian nhất định để tránh làm hệ thống bị quá tải hoặc chờ đợi vô ích. Sau thời gian này, circuit breaker sẽ thử lại; nếu service phục hồi thì đóng lại mạch, cho phép request đi tiếp.
[1388] Fallback là phương án thay thế, được dùng khi circuit breaker phát hiện lỗi và ngắt mạch.
Nên dùng fallback khi bạn muốn hệ thống vẫn có thể phản hồi cho user trong trường hợp có lỗi, ví dụ:
[1389] + Trả về dữ liệu mặc định, thông báo dễ hiểu,
[1390] + Đọc cached data thay vì gọi service sống,
[1391] + Hoặc thực hiện logic dự phòng khác.
[1392] Distributed Tracing
[1393] Để biết một request đã đi qua những service nào trong hệ thống microservices, ta sử dụng distributed tracing.
[1394] Các công cụ như Spring Cloud Sleuth sẽ tự động gắn một traceId (mã theo dõi) vào mỗi request khi nó bắt đầu. Khi request này đi qua từng service, traceId (và các spanId) sẽ được truyền kèm theo, ghi lại thông tin tại mỗi điểm dừng.
[1395] Sau đó, các log hoặc dữ liệu trace này được gửi đến hệ thống thu thập như Zipkin. Trên giao diện Zipkin, bạn có thể tra cứu theo traceId để xem toàn bộ luồng đi của request này qua từng service, thời gian xử lý ở mỗi bước, giúp dễ dàng debug, kiểm tra hiệu năng và phát hiện chỗ bottleneck.
[1396] Centralized Logging
[1397] Centralized Logging là giải pháp thu thập, xử lý và hiển thị log của tất cả các microservice về một nơi tập trung thay vì lưu rải rác trên từng server hoặc container. Điều này giúp dễ dàng theo dõi, tìm kiếm, phân tích log khi cần debug, audit, hoặc giám sát hệ thống.
[1398] Thường dùng ELK Stack. ELK Stack gồm 3 thành phần chính:
[1399] + Elasticsearch: Lưu trữ và cho phép tìm kiếm log mạnh mẽ, theo thời gian thực.
[1400] + Logstash: Thu thập, xử lý, chuyển đổi log từ nhiều nguồn trước khi đẩy vào Elasticsearch.
[1401] + Kibana: Giao diện trực quan để truy vấn, hiển thị, vẽ biểu đồ và dashboard từ dữ liệu log.
[1402] Messaging & Event-driven
[1403] Messaging & Event-driven là mô hình giúp các microservice giao tiếp, truyền thông tin với nhau thông qua các sự kiện (event) hoặc message thay vì gọi trực tiếp qua HTTP.
[1404] Các service sẽ gửi và nhận dữ liệu qua một hệ thống trung gian gọi là message broker (như Kafka, RabbitMQ), giúp tách biệt các service, tăng tính linh hoạt, mở rộng và giảm phụ thuộc lẫn nhau.
[1405] Security
[1406] Luồng kiểm tra token tại API Gateway với Spring Cloud Security:
[1407] Client gửi request đến API Gateway, kèm theo access token (thường là JWT hoặc OAuth2) trong header (ví dụ: Authorization).
[1408] API Gateway nhận request và chuyển request này qua các filter bảo mật được cấu hình bởi Spring Cloud Security (kết hợp với Spring Security).
[1409] Spring Cloud Security sẽ:
[1410] Tự động trích xuất token từ header.
[1411] Tự động xác thực token:
[1412] Nếu là JWT, Spring Cloud Security sẽ kiểm tra chữ ký, thời hạn, issuer, audience,… (dựa vào cấu hình public key/secret).
[1413] Nếu là OAuth2 opaque token, Spring Cloud Security sẽ tự động gọi đến Authorization Server (introspection endpoint) để xác thực token.
[1414] Tự động kiểm tra phân quyền (authorization):
[1415] Phân tích các claim, role trong token và kiểm tra xem user có quyền truy cập endpoint hay không (theo rule đã cấu hình).
[1416] Nếu token hợp lệ và user có đủ quyền:
[1417] Spring Cloud Security cho phép request được chuyển tiếp đến các service phía sau.
[1418] Nếu token không hợp lệ hoặc thiếu quyền:
[1419] Spring Cloud Security sẽ tự động chặn request và trả về lỗi 401 (unauthorized) hoặc 403 (forbidden) cho client.
[1420] Externalized Configuration / Profiles
[1421] Externalized Configuration / Profiles là cơ chế cho phép ứng dụng Spring Boot cấu hình các tham số hoạt động (URL DB, secret, port, endpoint…) bên ngoài code và theo từng môi trường (dev, test, prod), giúp dễ quản lý, dễ chuyển đổi môi trường mà không cần sửa mã nguồn.
[1422] Spring Boot hỗ trợ externalized configuration bằng cách tách cấu hình theo từng môi trường (dev, test, prod) qua các file như application-dev.yml, application-prod.yml.
[1423] Khi deploy, chỉ cần chọn profile phù hợp, hệ thống sẽ tự động nạp đúng cấu hình mà không cần sửa code.
[1424] Health Check, Monitoring
[1425] Health Check và Monitoring là các giải pháp giúp kiểm tra trạng thái hoạt động, hiệu năng và các chỉ số quan trọng của hệ thống microservices, đồng thời hỗ trợ cảnh báo sớm khi có sự cố.
[1426] Các công cụ thường dùng:
[1427] + Spring Boot Actuator:
[1428] Cung cấp sẵn các endpoint như /actuator/health, /actuator/metrics, giúp kiểm tra trạng thái sống/chết (health), các thông số hệ thống (CPU, memory, thread, DB, v.v.).
[1429] + Prometheus:
[1430] Thu thập metrics từ nhiều service (bao gồm từ Actuator), lưu trữ và hỗ trợ cảnh báo theo rule.
[1431] + Grafana:
[1432] Trực quan hóa dữ liệu metrics từ Prometheus, tạo dashboard theo dõi trạng thái, hiệu năng, lịch sử hoạt động hệ thống.
[1434] Spring Batch
[1435] Spring Batch chuyên dùng cho các tác vụ xử lý dữ liệu lớn, chạy theo lô (batch), có tính định kì, ví dụ như nhập xuất dữ liệu, gửi email hàng loạt, tổng hợp báo cáo, đồng bộ dữ liệu giữa các hệ thống.
[1436] Kiến trúc Spring Batch
[1437] Job: Một tác vụ batch lớn, gồm nhiều bước (step).
[1438] Step: Mỗi bước nhỏ trong job: đọc, xử lý, ghi.
[1439] ItemReader: Đọc dữ liệu (từ file, DB, API...).
[1440] ItemProcessor: Xử lý dữ liệu (chuyển đổi, validate...).
[1441] ItemWriter: Ghi dữ liệu ra (DB, file, gửi API...).
[1442] JobLauncher: Khởi động job.
[1443] JobRepository: Quản lý trạng thái, lịch sử job. 
Ví dụ:
[1444] Job: ImportCustomerJob
(Xử lý toàn bộ việc nhập dữ liệu khách hàng)
[1445] Step: ImportCustomerStep
(Gồm 3 thành phần chính: đọc file, xử lý, ghi vào DB)
[1446] ItemReader: CustomerItemReader
(Đọc từng dòng từ file CSV)
[1447] ItemProcessor: CustomerItemProcessor
(Kiểm tra, validate thông tin khách hàng, ví dụ: email hợp lệ, tuổi > 18...)
[1448] ItemWriter: CustomerItemWriter
(Ghi thông tin khách hàng hợp lệ vào bảng Customer trong database)
[1449] JobLauncher: Được sử dụng để kích hoạt job (bằng code, scheduler, command line…)
[1450] JobRepository: Lưu trạng thái thực thi, lịch sử từng job (thành công/thất bại, số bản ghi xử lý...)
[1452] Cấu hình Job và Step
[1453] Khai báo Job và Step bằng Java Config
[1454] Sử dụng JobBuilderFactory để tạo job, đặt tên, khai báo trình tự các step và điều kiện chuyển tiếp giữa các step.
[1455] Sử dụng StepBuilderFactory để tạo step, gán tên, định nghĩa reader, processor, writer, cấu hình chunk (kích thước lô xử lý).
[1457] Chunk là cách chia nhỏ dữ liệu thành từng lô (batch nhỏ), ví dụ mỗi lần đọc/xử lý/ghi 10 bản ghi, giúp tăng hiệu suất (ít giao tiếp DB, rollback dễ dàng nếu lỗi).
[1458] Ví dụ sử dụng .chunk(10) dữ liệu sẽ được xử lý theo từng lô 10 bản ghi.
[1459] Quản lý trạng thái, restart job
[1460] Quản lý trạng thái:
[1461] JobRepository là nơi lưu trữ trạng thái, lịch sử thực thi của các job/step.
[1462] Một job trong Spring Batch có nhiều trạng thái như:
[1463] STARTED: Đang chạy.
[1464] COMPLETED: Chạy xong thành công.
[1465] FAILED: Bị lỗi.
[1466] STOPPED, ABANDONED, UNKNOWN, ... (các trạng thái phụ khác).
[1467] Restart job khi bị lỗi
[1468] Khi job bị lỗi (FAILED), Spring Batch có thể restart lại job mà không cần chạy lại từ đầu toàn bộ dữ liệu.
[1469] Nhờ vào việc lưu checkpoint (vị trí đã xử lý) và trạng thái step trong JobRepository, khi restart:
[1470] + Các step đã COMPLETED sẽ được bỏ qua, chỉ chạy lại step bị lỗi hoặc chưa hoàn thành.
[1471] + Các chunk đã commit thành công sẽ không bị xử lý lại.
[1473] Xử lý lỗi (Skip, Retry, Transaction)
[1474] Skip - bỏ qua record lỗi, không dừng cả job
[1475] Khi gặp lỗi xử lý ở một bản ghi (ví dụ: dữ liệu sai format, không parse được…), thay vì dừng cả job, Spring Batch cho phép bỏ qua (skip) bản ghi đó và tiếp tục xử lý các bản ghi khác.
[1476] Cấu hình qua .faultTolerant().skip(Exception.class).skipLimit(5) nghĩa là cho phép bỏ qua tối đa 5 lỗi kiểu Exception.
[1478] Retry – Thử lại khi gặp lỗi tạm thời
[1479] Đối với lỗi tạm thời (ví dụ: kết nối DB/API bị timeout, network chập chờn…), Spring Batch cho phép tự động retry (thử lại) một số lần trước khi bỏ cuộc hoặc skip.
[1480] Cấu hình qua .retry(Exception.class).retryLimit(3) để thử lại tối đa 3 lần với lỗi Exception.
[1482] Transaction – Đảm bảo tính nhất quán khi ghi nhiều bản ghi
[1483] Chunk được xử lý trong cùng một transaction. Nếu một bản ghi trong chunk bị lỗi mà không được skip, toàn bộ chunk sẽ bị rollback, dữ liệu không bị ghi thiếu/cập nhật sai.
[1484] Spring Batch quản lý transaction tự động cho mỗi chunk, đảm bảo tính nhất quán (atomicity): hoặc ghi thành công cả chunk, hoặc rollback cả chunk.
[1485] Scheduling (Lên lịch chạy)
[1486] Để tự động hóa việc chạy các job batch đúng theo lịch trình (ví dụ: hàng ngày, hàng giờ…), ta có thể sử dụng các công cụ lập lịch như Spring Scheduler
[1488] Parallel & Partitioning (Chạy song song)
[1489] Thay vì xử lý tuần tự toàn bộ dữ liệu, Spring Batch cho phép chia nhỏ (partition) dữ liệu hoặc step thành nhiều phần nhỏ (partition/sub-task) và xử lý các phần đó song song (parallel).
Các cách chạy song song phổ biến:
[1490] Multi-threaded Step
[1491] Một step được cấu hình để nhiều thread xử lý các chunk song song.
[1493] Partitioning
[1494] Chia dữ liệu thành nhiều partition, mỗi partition là một step con, chạy song song trên nhiều thread hoặc nhiều node khác nhau.
[1495] Phù hợp với dữ liệu lớn, cần chia khối lượng rõ ràng (theo range ID, theo file, theo khu vực…).
[1497] Logging & Monitoring
[1498] Để quản lý log và theo dõi batch, có thể cấu hình log riêng cho batch bằng logback-spring.xml hoặc application-batch.yml.
[1499] Spring Batch tự động log tiến trình, trạng thái, lỗi của job.
[1500] Có thể tích hợp với monitoring (Actuator, Prometheus…) để theo dõi và cảnh báo khi batch có sự cố.
[1501] Kết nối nguồn dữ liệu
[1502] Spring Batch hỗ trợ đọc/ghi dữ liệu từ nhiều nguồn như file CSV, Excel, XML, database, message queue…
[1503] Ví dụ đọc DB:
[1505] Nhiều dự án thực tế sẽ cấu hình DataSource riêng cho batch để tách biệt với hệ thống giao dịch chính, giúp batch chạy ổn định và dễ quản lý.
[1506] Ví dụ trong application-batch.yml:
[1508] Batch Parameters
[1509] Batch Parameters là các giá trị/biến truyền vào khi khởi chạy job, dùng để tùy biến hành vi (ví dụ: file name, ngày xử lý, ID phiên bản…).
[1510] Tham số có thể truyền qua:
[1511] + Command line khi chạy jar:
[1512] java -jar my-batch.jar "inputFile=customers.csv" "runDate=2024-06-01"

[1524] System Architect, Software design & Best practice coding
[1525] Kiến trúc tổng quan hệ thống
[1526] Monolithic Architecture: Kiến trúc đơn khối.
[1527] Toàn bộ ứng dụng (từ UI, logic nghiệp vụ, đến truy xuất dữ liệu) được đóng gói và deploy thành một khối duy nhất (một file, một process).
[1528] Modular Monolith / Domain-based Monolith.
[1529] Modular Monolith: Là một dạng Monolithic, nhưng hệ thống được thiết kế thành nhiều module độc lập rõ ràng bên trong cùng một khối deploy
[1530] (deploy một lần, chạy một process).
[1531] Domain-based Monolith: Là một kiểu Modular Monolith, nhưng các module được phân chia dựa trên “domain” nghiệp vụ theo phong cách DDD (Domain-Driven Design).
[1532] Microservices Architecture: Kiến trúc vi dịch vụ.
[1533] Microservices là kiến trúc hệ thống mà mỗi chức năng (service) được tách ra thành một dịch vụ nhỏ, độc lập, giao tiếp qua API (thường là REST, gRPC, hoặc GraphQL)
[1534] Ưu điểm:
[1535] + Độc lập: Mỗi service triển khai riêng biệt nên không ảnh hưởng tới service khác nếu có lỗi.
[1536] + Dễ mở rộng: có thể scale theo từng service, ví dụ service thanh toán có thể mở rộng riêng nếu lưu lượng tăng cao, không cần scale toàn hệ thống
[1537] + Dễ triển khai: chỉ cần build/test và deploy từng service độc lập, thay vì với cả khối lớn như monolith
[1538] + Linh hoạt công nghệ: Mỗi service có thể chọn ngôn ngữ, DB, FW phù hợp
[1539] + Khả năng phục hồi: Nếu 1 service có sự cố, các service khác vẫn hoạt động ổn định. Khó sập hơn monolith
[1540] Nhược điểm:
[1541] + Quản lý phức tạp, yêu cầu Devops mạnh: Cần hệ thống CI/CD, monitoring, logging, container orchestration (Kubernetes, Docker…) chuyên nghiệp để vận hành trơn tru
[1542] + Do giao tiếp qua mạng nên có vấn đề về độ trễ (network latency), lỗi truyền thông tin hoặc bảo mật mạng
[1543] + Dữ liệu phân tán nên khó đảm bảo nhất quán hơn monolith
[1545] Service-Oriented Architecture (SOA): Kiến trúc hướng dịch vụ.
[1546] Ứng dụng chia nhỏ thành các service độc lập, giao tiếp qua chuẩn chung (SOAP, REST...).
[1547] Ví dụ:
Hệ thống ngân hàng, mỗi chức năng là một service: chuyển tiền, quản lý tài khoản, thanh toán hóa đơn…
[1548] So sánh với Microservices:
[1549] SOA và Microservices đều hướng dịch vụ, nhưng Microservices là phiên bản nhẹ, tách nhỏ tối đa, linh hoạt, hướng đến Devops hơn SOA truyền thống.
[1550] Ví dụ:
[1551] SOA: Một “Order Service” có thể xử lý tất cả logic về đơn hàng, quản lý cả đơn, vận chuyển, thanh toán, báo cáo...
[1552] Microservices: “Order Service” chỉ lo đặt đơn, “Payment Service” chỉ xử lý thanh toán, “Shipping Service” chỉ lo vận chuyển – tách biệt hoàn toàn, mỗi team có thể phát triển và deploy độc lập.
[1553] Serverless/Cloud- Architecture: Kiến trúc không máy chủ.
[1554] Serverless là mô hình triển khai ứng dụng mà không phải quản lý máy chủ vật lý hoặc máy chủ ảo.
[1555] Chỉ cần viết các function nhỏ (function as a service – FaaS), hệ thống cloud (AWS Lambda, Azure Functions, GCP Cloud Functions…) sẽ tự động chạy code khi có sự kiện và tự động scale, quản lý hạ tầng.
[1556] Ví dụ:
[1557] Khi có file upload lên S3 (AWS), một function Lambda tự động kích hoạt để xử lý file (resize ảnh, chuyển đổi format, gửi thông báo...).
[1558] Kiến trúc hệ thống phân tán
[1559] Hệ thống phân tán tổ chức các thành phần phần mềm chạy trên nhiều máy tính (node) khác nhau, phối hợp với nhau để thực hiện các tác vụ chung.
[1560] Những thành phần này có thể là các service, microservice, module hay process… cùng giao tiếp qua mạng (TCP/IP, HTTP, gRPC, v.v) để chia sẻ dữ liệu, phân chia công việc, đảm bảo hiệu suất và độ tin cậy.
[1561] Các đặc trưng
[1562] Tính mở rộng (Scalability): Có thể bổ sung thêm node để tăng hiệu năng hoặc dung lượng.
[1563] Tính sẵn sàng (Availability): Hệ thống hoạt động kể cả khi một số node bị lỗi.
[1564] Tính nhất quán (Consistency): Đảm bảo dữ liệu đồng bộ giữa các node.
[1565] Tính chịu lỗi (Fault Tolerance): Khi một thành phần gặp sự cố, hệ thống vẫn vận hành bình thường.
[1566] Tính trong suốt (Transparency): Người dùng không nhận ra sự phân tán của các thành phần.
[1567] Một số design pattern quan trọng
[1568] Replication Pattern (Sao chép dữ liệu)
[1569] Sao chép dữ liệu hoặc service lên nhiều node để tăng độ sẵn sàng và khả năng chịu lỗi.
[1570] Sharding Pattern (Phân mảnh dữ liệu)
[1571] Chia nhỏ dữ liệu thành nhiều phần, lưu trên các node khác nhau để tăng khả năng mở rộng và hiệu năng.
[1572] Service Discovery Pattern (Tìm kiếm dịch vụ)
[1573] Các service đăng ký vị trí với registry và tự động phát hiện nhau qua registry này.
[1574] API Gateway Pattern
[1575] Cổng truy cập duy nhất để nhận request từ client và phân phối đến các service backend.
Ví dụ: Kong, NGINX.
[1576] Circuit Breaker Pattern (Ngắt mạch)
[1577] Tạm dừng request đến service khi service đó bị lỗi liên tục, giúp bảo vệ hệ thống.
[1578] Message Queue Pattern (Hàng đợi thông điệp)
[1579] Truyền thông điệp bất đồng bộ giữa các service, giảm phụ thuộc trực tiếp.
Ví dụ: RabbitMQ, Kafka.
[1580] Saga Pattern
[1581] Quản lý giao dịch phân tán theo từng bước nhỏ, rollback linh hoạt khi có lỗi.
Ví dụ: Đặt hàng nhiều bước trong thương mại điện tử.
[1582] Event Sourcing Pattern
[1583] Lưu lại toàn bộ sự kiện thay đổi trạng thái, giúp khôi phục, audit, và đảm bảo nhất quán cuối cùng.
[1584] Domain-Driven Design (DDD)
[1585] Là cách thiết kế phần mềm / tổ chức code tập trung vào mô hình nghiệp vụ (domain) và sự hiểu biết sâu sắc về nghiệp vụ đó.
[1586] Nhấn mạnh việc chia nhỏ hệ thống theo domain (lĩnh vực nghiệp vụ), giúp codebase sát thực tế, dễ hiểu, dễ bảo trì.
[1587] Các khái niệm
[1588] Entities
[1589] Đối tượng có “danh tính” (identity) duy nhất, tồn tại lâu dài trong hệ thống.
[1590] Ví dụ Customer, Order (dù thông tin thay đổi, ID vẫn không đổi).
[1591] Value Objects
[1592] Đối tượng không có danh tính, chỉ quan tâm tới giá trị, so sánh bằng giá trị.
[1593] Ví dụ Address, Money (hai địa chỉ giống hệt nhau coi là bằng nhau).
[1594] Aggregates
[1595] Một nhóm các entity và value object có liên quan.
[1596] Dữ liệu bên trong aggregate sẽ được toàn vẹn và nhất quán (consistency).
[1597] Ví dụ Order aggregate gồm Order (entity), danh sách OrderItem (entity hoặc value object), ShippingAddress (value object).
[1598] Repositories
[1599] Lớp trung gian để truy xuất, lưu trữ entity/aggregate khỏi persistence (DB, file…)
[1600] Ví dụ OrderRepository để lưu/truy vấn Order.
[1601] Services
[1602] Chứa logic nghiệp vụ không thuộc về entity/value object nào cụ thể.
[1603] Ví dụ PaymentService để xử lý thanh toán.
[1604] Domain Event
[1605] Sự kiện quan trọng xảy ra trong domain, cho phép các thành phần khác biết và hành động theo.
[1606] Ví dụ OrderPlaced - Khách hàng đặt đơn hàng thành công.
[1607] Khi đặt hàng xong, Order Service phát ra một event:
OrderPlacedEvent (chứa thông tin đơn hàng, khách hàng…).
[1608] Các “listener” khác nhau sẽ nhận sự kiện này và thực hiện việc riêng:
[1609] EmailService nhận event, gửi email xác nhận.
[1610] InventoryService nhận event, cập nhật số lượng tồn kho.
[1611] ShippingService nhận event, tạo đơn vận chuyển.
[1612] AnalyticsService nhận event, ghi nhận dữ liệu.

[1653] Bounded Context
[1654] Một giới hạn rõ ràng về ngữ nghĩa và logic của một phần domain. Mỗi bounded context có mô hình, code, ngôn ngữ riêng biệt.
[1655] Tác dụng: Tránh nhầm lẫn/chồng chéo giữa các domain khác nhau (ví dụ: “Order” ở context bán hàng khác với “Order” ở context kho vận).
[1656] Ubiquitous Language
[1657] Một ngôn ngữ chung, nhất quán giữa lập trình viên và chuyên gia nghiệp vụ, dùng xuyên suốt code, tài liệu, trao đổi.
[1658] Tác dụng: Giúp tất cả thành viên hiểu nhau, code sát nghiệp vụ thực tế, giảm nhầm lẫn.
[1659] Mẫu tổ chức code
[1662] Một số kiến trúc tổ chức code khác
[1663] Layered Architecture (N-Tier)
[1664] Ý tưởng:
Chia ứng dụng thành các lớp (layer) rõ ràng, mỗi lớp đảm nhiệm một vai trò.
[1665] Thường gặp nhất:
[1666] Presentation Layer: Giao diện (UI, API)
[1667] Application Layer: Điều phối luồng nghiệp vụ
[1668] Domain/Business Layer: Logic nghiệp vụ chính
[1669] Data Access Layer: Truy xuất dữ liệu (DB, file…)
[1671] Hexagonal / Ports & Adapters
[1672] Ý tưởng:
Ứng dụng là một “lõi” (core/domain) không phụ thuộc vào các yếu tố bên ngoài. Các cổng (port) và bộ chuyển đổi (adapter) giúp core kết nối ra ngoài (UI, DB, message broker, API…).
[1673] Cách tổ chức:
[1674] Core chỉ biết về interface (port).
[1675] Adapter đảm nhiệm giao tiếp thực tế (REST, DB, file, …).
[1676] Ưu điểm: Tách biệt rõ giữa logic nghiệp vụ và hạ tầng, dễ test, dễ thay thế adapter.
[1677] Ví dụ: Thay đổi từ lưu file sang lưu DB mà không ảnh hưởng core.
[1679] Clean / Onion Architecture
[1680] Ý tưởng:
Mọi phụ thuộc đều hướng vào “lõi” domain/business. Các lớp ngoài cùng là hạ tầng, càng vào trong càng gần domain logic.
[1681] Cấu trúc:
[1682] Core (Entities/Domain): Logic nghiệp vụ thuần, không phụ thuộc ai cả.
[1683] Use Cases/Application: Quy trình nghiệp vụ, điều phối.
[1684] Interface Adapters: Chuyển đổi giữa use case và hạ tầng.
[1685] Frameworks/Drivers: Hạ tầng, thư viện, giao tiếp bên ngoài.
[1686] Ưu điểm: Dễ thay đổi hạ tầng, dễ test, domain độc lập, dễ mở rộng.
[1687] Ví dụ:
Dễ đổi từ REST sang gRPC, từ MySQL sang MongoDB mà domain không đổi.
[1689] CQRS
[1690] Ý tưởng:
Tách biệt hai phần:
[1691] Command: Xử lý lệnh thay đổi trạng thái (C, U, D).
[1692] Query: Truy vấn dữ liệu (R).
[1693] Ưu điểm:
[1694] Đọc và ghi có thể tối ưu riêng, dễ scale, dễ tối ưu hóa cho từng mục đích.
[1695] Thường dùng với:
[1696] Event Sourcing, hệ thống cần throughput cao, nghiệp vụ phức tạp.
[1697] Ví dụ:
Khi đặt hàng, command “CreateOrder” ghi dữ liệu.
[1698] Query “GetOrderHistory” đọc dữ liệu đã được tổng hợp sẵn.
[1700] Event-Driven Architecture
[1701] Ý tưởng:
Các thành phần trong hệ thống giao tiếp với nhau bằng event (sự kiện), không gọi trực tiếp.
[1702] Cách hoạt động:
[1703] Khi có sự kiện (ví dụ: “OrderCreated”), các service/subscriber lắng nghe sẽ xử lý theo nhu cầu riêng.
[1704] Ưu điểm:
[1705] Phi đồng bộ, giảm coupling, dễ mở rộng.
[1706] Xử lý song song, phản ứng nhanh với sự kiện thực tế.
[1707] Ví dụ:
Đặt hàng xong, phát sự kiện “OrderCreated”. Service vận chuyển, gửi email, phân tích dữ liệu đều bắt sự kiện này để xử lý riêng.
[1709] Design Principles:
[1710] SOLID
[1711] S – Single Responsibility Principle (SRP)
[1712] Mỗi class chỉ nên có một trách nhiệm duy nhất.
[1713] Ví dụ một class không nên vừa lấy dữ liệu từ database, xử lý dữ liệu rồi in ra. Thay vào đó chia thành các class riêng, mỗi class giữ một nhiệm vụ nhất định.
[1714] O – Open/Closed Principle (OCP)
[1715] Mở rộng thêm chức năng mới được, nhưng không cần sửa code cũ.
[1716] Open for extension, close for modification.
[1717] Ví dụ: Muốn thêm cách tính thuế mới, chỉ cần tạo class mới kế thừa hoặc implement interface, không phải sửa class cũ.
[1718] L – Liskov Substitution Principle (LSP)
[1719] Lớp con có thể thay thế cho lớp cha mà không làm sai logic chương trình.
[1720] Ví dụ: Có class Bird và Penguin extends Bird.
[1721] Nếu code nào dùng Bird thì dùng Penguin cũng phải an toàn (ví dụ không nên có hàm fly() ở Bird vì chim cánh cụt không bay được).
[1722] I – Interface Segregation Principle (ISP)
[1723] Nên chia nhỏ interface, tránh ép các class phải implement những phương thức không dùng.
[1724] Ví dụ có interface Printer, Scanner riêng. Máy in thì chỉ cần implement Printer, không phải implement Scanner.
[1725] D – Dependency Inversion Principle (DIP)
[1726] Các module cấp cao không nên phụ thuộc vào các module cấp thấp, cả hai nên phụ thuộc vào abstraction.
[1727] Ví dụ 1:
[1728] Ổ cắm điện trên tường là abstraction (chuẩn chung)
[1729] Thiết bị điện như quạt, tivi, sạc điện thoại là module cấp thấp
[1730] Người sử dụng là module cấp cao
[1731] Người sử dụng chỉ cần biết cắm thiết bị vào ổ điện là dùng được, không cần quan tâm bên trong quạt hay tivi cấu tạo ra sao.
Ổ cắm là chuẩn chung, miễn thiết bị nào tương thích là cắm vào dùng được.
[1732] Ví dụ 2:
[1733] Module cấp cao: OrderService
[1734] Abstraction: PaymentGateway (interface)
[1735] Module cấp thấp: PaypalPayment, VNPayPayment
[1736] (implement PaymentGateway)
[1737] OrderService chỉ biết đến PaymentGateway, không quan tâm bạn dùng Paypal, VNPay hay gì khác.
[1738] Khi muốn thay đổi cách thanh toán, chỉ cần implement interface mới, không sửa OrderService.
[1739] DRY (Don’t Repeat Yourself)
[1740] Ý nghĩa: Đừng lặp lại chính mình.
Tránh lặp lại code, logic, dữ liệu ở nhiều chỗ. Nếu phải sửa đổi, chỉ sửa một nơi duy nhất.
[1741] Ví dụ: Nếu validation logic cho email xuất hiện ở nhiều class, hãy tách ra thành hàm chung.
[1742] KISS (Keep It Simple, Stupid)
[1743] Ý nghĩa: Giữ cho mọi thứ đơn giản, dễ hiểu.
Tránh phức tạp hóa vấn đề, code nên rõ ràng, dễ đọc, dễ bảo trì.
[1744] Ví dụ: Nếu giải quyết bài toán cộng 2 số, chỉ cần dùng phép cộng, không cần viết thêm class, pattern phức tạp.
[1745] YAGNI (You Aren’t Gonna Need It)
[1746] Ý nghĩa: Đừng code những thứ bạn nghĩ sẽ cần trong tương lai, nhưng hiện tại chưa cần.
Chỉ nên phát triển tính năng khi thực sự có nhu cầu sử dụng.
[1747] Ví dụ: Nếu app chưa cần đa ngôn ngữ, đừng vội viết hệ thống dịch phức tạp ngay từ đầu.
[1748] Design Patterns cổ điển
[1749] Được hiểu như những bộ dụng cụ kinh nghiệm giải quyết các vấn đề thường gặp, giúp code sạch, dễ bảo trì và mở rộng.
[1750] Các mẫu khởi tạo (creational patterns)
[1751] Builder
[1752] Builder dùng để tạo object phức tạp theo từng bước mà không cần constructor có nhiều tham số. Thường dùng khi object có nhiều field, đặc biệt optonal field. Thường thấy ở DTO, sử dụng Lombok @Builder.
[1753] Lợi ích:

[2366] Docker
[2367] Là nền tảng để đóng gói, phân phối và chạy các ứng dụng trong các chiếc “hộp” gọi là container.
[2368] Container là một môi trường biệt lập, chứa tất cả các thành phần cần thiết để chạy ứng dụng (mã nguồn, thư viện, dependencies...) giúp ứng dụng đảm bảo chạy đồng nhất ở mọi môi trường.
[2369] Core concept:
[2370] Image: một snapshot của ứng dụng, bao gồm source code và toàn bộ môi trường để chạy nó
[2371] Container: một instance, tức là 1 phiên bản chạy của image
[2372] Dockerfile: Một text file chứa hướng dẫn để build một image
[2373] Dockerhub: Kho lưu trữ image công khai
[2374] Docker compose: Sử dụng một file docker-compose.yml để định nghĩa và quản lý multi-container cần dùng để chạy một ứng dụng
[2375] Volume: nơi lưu dữ liệu nằm ngoài container, giống như một ổ cứng riêng không bị mất dữ liệu khi xóa hoặc tạo lại container. Thường dùng lưu database records hoặc các file upload trong hệ thống.

[2497] Best practice khi sử dụng Docker:
[2498] + Tối ưu hóa docker image:
[2499] Sử dụng multi-stage build:
Chỉ copy các file cần thiết vào image cuối cùng, loại bỏ tool, source code, thư viện build không cần thiết.
[2500] Chọn base image tối ưu:
Ưu tiên các image nhẹ như alpine, slim, hoặc các image chính thức được cập nhật thường xuyên.
Ví dụ: node:20-alpine, python:3.12-slim, openjdk:17-jre-slim.
[2501] Chỉ copy những gì cần thiết:
Sử dụng .dockerignore để loại trừ file/thư mục không cần thiết (node_modules, .git, test, docs...).
[2502] Layer caching thông minh:
Sắp xếp lệnh Dockerfile để tận dụng cache, copy file cấu hình/lock trước, cài dependency rồi mới copy source code.
[2503] Minify, compress, clean up:
Xóa cache build, temp file sau khi cài dependency (sử dụng lệnh rm -rf, --no-cache khi có thể).
[2505] + Bảo mật docker image:
[2506] Chỉ cài những gì cần thiết:
Tránh cài tool, package dư thừa. Chỉ giữ đúng runtime và dependency cho app.
[2507] Luôn dùng bản image mới nhất:
Update image base thường xuyên để nhận các bản vá bảo mật.
[2508] User không phải root:
Thêm lệnh USER appuser (sau khi tạo user bằng RUN adduser ...) để hạn chế quyền trong container.
[2509] Chặn expose không cần thiết:
Chỉ mở đúng cổng app, không expose thêm cổng hoặc dịch vụ không dùng.
[2510] Quản lý secrets đúng cách:
Không hard-code mật khẩu, token vào image. Sử dụng biến môi trường hoặc external secrets.
[2511] Kiểm tra lỗ hổng security:
Sử dụng công cụ như Trivy, Snyk để scan image, phát hiện package lỗi thời, lỗ hổng bảo mật.
[2513] + Với Dockerfile:
[2514] Gọn gàng, dễ đọc:
Thêm chú thích, phân tách rõ các bước build, chỉ giữ lại những lệnh cần thiết.
[2515] Không hard-code sensitive info:
Không đẩy file cấu hình bí mật, mật khẩu, private key vào image.
[2516] Dọn rác sau khi build:
Ví dụ sau khi apt-get install, thực hiện apt-get clean và xóa /var/lib/apt/lists/*.
[2517] Sử dụng Healthcheck:
Thêm lệnh HEALTHCHECK để Docker tự kiểm tra trạng thái app.
[2518] Kubernetes
[2519] Là một open source platform quản lý nhiều container, tự động deploy, scale và quản lý các ứng dụng được container hóa (như sử dụng docker)
[2520] So với docker:
[2521] + Docker: là công cụ để tạo và chạy container
[2522] + K8s: là platform có thể quản lý nhiều container Docker (hoặc non-Docker container), trên nhiều server khác nhau
[2524] So với docker compose:
[2526] Core concept:
[2527] + Cluster (cụm máy chủ): tập hợp các servers được quản lý cùng nhau
[2528] Một hệ thống lớn có thể có nhiều cluster, mỗi cluster có nhiều server. Cluster giống như một khu vườn, trong khu vườn có nhiều mảnh đất nhỏ để trồng từng loại cây. Từng mảnh đất này giống như các server.
[2529] + Server (Node): máy chủ vật lý hoặc ảo, có thể chạy nhiều ứng dụng
[2530] + Pod: Là đơn vị nhỏ nhất chứa một hoặc nhiều container.
[2531] Giống như mỗi chậu cây trên 1 mảnh đất (có thể chứa 1 cây hoặc một cụm cây)
[2532] + Container: một ứng dụng hoặc dịch vụ riêng lẻ (như Spring boot app hoặc Postgre s database...).
[2533] Giống như một cây trong chậu.
[2534] + Deployment: deploy toàn bộ ứng dụng.
[2535] Giống như kế hoạch trồng cây số lượng lớn trong vườn. Bạn khai báo số lượng chậu cây (Pod), loại cây (Container) sẽ được trồng, K8s sẽ tự động trồng đúng số lượng theo yêu cầu.
[2536] + Service: bộ định tuyến giúp các ứng dụng bên ngoài hoặc các Pod khác biết cách truy cập đến một Pod.
[2537] Giống như biển chỉ dẫn trong vườn, giúp mọi người biết đường tới các chậu cây.
[2538] + Namespace: chia nhỏ cluster thành các môi trường (dev, test, prod...) hoặc phân quyền truy cập cho từng team, giúp quản lý dễ dàng hơn
[2539] Giống như các khu vực riêng biệt trong vườn: vườn rau, vườn hoa, vườn cây cảnh...
[2540] + Volume: nơi lưu trữ dữ liệu dùng chung hoặc lâu dài cho các Container
[2541] Giống kho phân bón có thể dùng chung để bón cho các chậu cây khi cần.
[2542] + ConfigMap & Secret:  ConfigMap lưu trữ cấu hình không nhạy cảm, Secret lưu trữ thông tin nhạy cảm
[2543] + Ingress: quản lý truy cập từ bên ngoài vào các dịch vụ trong cluster
[2544] Giống cổng kiểm soát ra vào CHÍNH của cả khu vườn
[2545] Tại sao dùng Kubernetes?
[2546] + Tự động hóa quản lý container: triển khai, cập nhật, rollback, scale tự động.
[2547] + Đảm bảo tính sẵn sàng: Nếu 1 container chết, K8s tự động khởi động lại hoặc thay thế.

[2556] + Clients / API (kubectl, dashboard)

[2558] Dashboard/Devops tool: Giao diện quản trị, CICD, monitoring

[2560] API server: cửa giao tiếp, nhận lệnh từ client/devops
[2561] Scheduler: Quyết định pod nào chạy ở node nào dựa vào tài nguyên, rule, policies
[2562] Controller Manager: Tự động thực hiện các hành động đảm bảo trạng thái hệ thống đúng như khai báo về số lượng pod, tự động xử lý lỗi...
[2563] etcd: Hệ thống lưu trữ key-value phân tán, dùng để lưu trữ toàn bộ trạng thái của cluster (cấu hình, secret, trạng thái pod...), đảm bảo tính nhất quán của dữ liệu trong cluster

[2565] kubelet: “người quản lý”, nhận lệnh từ Master Node, monitor các Pod
[2566] kube-proxy: Network manager, forward yêu cầu đến đúng cổng
[2567] Container Runtime: Container running platform, ví dụ như Docker.
[2568] + Pods
[2569] Là đơn vị nhỏ nhất, thường chứa 1 container (có thể nhiều), Pod được tạo hoặc hủy bởi K8s tùy vào kế hoạch Deployment/ReplicaSet
[2570] + Service & Network
[2571] Service: địa chỉ ảo, giúp Pods giao tiếp và load balancing
[2572] Ingress, LoadBalancer: Export services ra ngoài internet
[2573] + Volume
[2574] emptyDir: được tạo khi Pod được tạo và tồn tại đến khi Pod bị xóa, thường dùng làm bộ nhớ tạm
[2576] hostPath: Dùng để mount một thư mục trên node (server) vào Pod, có thể nguy hiểm nếu không cấu hình cẩn thận
[2578] configMap, secret: Dùng để mount các file cấu hình hoặc các thông tin nhạy cảm (password, key,...) vào container. Đây là các file cấu hình secret của từng container, cần phân biệt với ConfigMap & Secret của Kubernetes.

[2722] Helm
[2723] Helm là một công cụ quản lý package (giống như apt, yum, npm nhưng cho Kubernetes).
[2724] Helm giúp bạn đóng gói, chia sẻ, cài đặt, nâng cấp, rollback các ứng dụng trên Kubernetes một cách dễ dàng bằng các "chart".
[2725] Core concept: Helm Chart
[2726] Helm Chart là một “gói” gồm các file YAML định nghĩa tài nguyên (Deployment, Service, ConfigMap, Secret...) và các template hỗ trợ biến, logic.
[2727] Chart giúp bạn dễ dàng tái sử dụng, cấu hình linh hoạt và quản lý ứng dụng phức tạp trên K8s.
[2728] Cấu trúc Helm Chart:
[2730] Các lệnh cơ bản:
[2731] + Cài đặt Helm:
[2732] curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
[2733] + Làm việc với chart:
[2734] Tạo chart mới: helm create mychart
[2735] Cài chart lên cluster: helm install release-name ./mychart
[2736] Nâng cấp chart (update config, version..): helm upgrade release-name ./mychart
[2737] Gỡ chart: helm uninstall release-name
[2738] Xem list release đã cài: helm list
[2739] Rollback: helm rollback release-name <revision>
[2740] Tùy biến cấu hình với values.yaml
[2741] Có thể ghi đè giá trị trong values.yaml bằng file khác hoặc trực tiếp qua dòng lệnh:
[2742] helm install release-name ./mychart -f my-values.yaml
[2743] hoặc
[2744] helm install release-name ./mychart --set image.tag=2.0
[2745] Các giá trị này sẽ được đưa vào template YAML qua cú pháp {{ .Values.xxx }}.
[2746] Làm việc với template (biến và logic)
[2747] Trong thư mục templates/, các file .yaml có thể dùng biến, vòng lặp, điều kiện bằng cú pháp Go template.

[2770] Infrastructure as Code
[2771] Infrastructure as Code là việc mô tả hạ tầng (server, network, storage, cấu hình ứng dụng, v.v.) bằng file code/script thay vì cấu hình thủ công.
[2772] Nhờ IaC, bạn có thể:
[2773] Tự động tạo mới, sửa đổi, xóa hạ tầng chỉ bằng code.
[2774] Dễ kiểm soát, version, rollback, review và chia sẻ.
[2775] Đảm bảo mọi môi trường (dev, staging, prod) giống nhau, tránh sai sót thủ công.
[2776] Áp dụng với Kubernetes & Helm:
[2777] Các file YAML Kubernetes (Deployment, Service, Ingress, ConfigMap, v.v.) chính là IaC.
[2778] Helm chart là “gói” IaC: bạn chỉ cần giữ chart trên Git, mọi người đều có thể deploy hệ thống giống nhau.
[2779] Khi cần thay đổi cấu hình (số Pod, image, port, DB,...) chỉ chỉnh sửa file values hoặc template và cập nhật lên Git.
[2780] Các tool IaC phổ biến:
[2781] Terraform: Tạo hạ tầng cloud (AWS, GCP, Azure, v.v.)
[2782] Ansible: Tự động cấu hình server, app.
[2783] Helm: Quản lý ứng dụng trên K8s.
[2784] Kustomize: Tùy biến YAML trên K8s.
[2786] CI/CD
[2787] CI/CD là quy trình tự động hóa từ lúc code được commit lên Git → build → test → deploy lên server/cluster.
[2788] CI (Continuous Integration): Tự động kiểm tra, build, test code khi có thay đổi.
[2789] CD (Continuous Deployment/Delivery): Tự động deploy code/app lên môi trường (dev, staging, prod).
[2790] Lợi ích:
[2791] Triển khai nhanh, giảm lỗi, rollback dễ dàng.
[2792] Đảm bảo chất lượng code (test, lint, kiểm tra bảo mật...).
[2793] Dễ mở rộng, chuẩn hóa quy trình làm việc nhóm.

[2911] Blue-Green Deployment
[2912] Tạo hai môi trường song song: “Blue” (cũ) và “Green” (mới).
[2913] Khi deploy xong ở môi trường “Green”, chuyển trafffic từ “Blue” sang “Green”.
[2914] Giúp rollback nhanh nếu có sự cố, giảm rủi ro.
[2915] Canary Deployment
[2916] Chỉ deploy phiên bản mới cho một phần nhỏ người dùng (ví dụ: 5% traffic).
[2917] Theo dõi phản hồi, nếu ổn thì tăng dần số người dùng sử dụng bản mới.
[2918] Phù hợp khi cần kiểm tra, thử nghiệm, giảm tác động lỗi.
[2919] Recreate
[2920] Dừng toàn bộ phiên bản cũ rồi mới chạy phiên bản mới.
[2921] Có downtime, ít dùng trong hệ thống cần high availability.

[2924] Luôn có phương án rollback nhanh.

[2930] TDD
[2931] Là phương pháp phát triển phần mềm mà bạn viết test trước, sau đó mới code để làm test đó chạy pass.
[2932] Quy trình:
[2933] Viết test (thường là unit test).
[2934] Chạy test (fail vì chưa có code).
[2935] Viết code hoàn thiện.
[2936] Chạy lại test (pass).
[2937] Refactor code/test nếu cần.
[2938] Lợi ích: Code chất lượng hơn, ít bug, dễ bảo trì.
[2939] Ví dụ: Giả sử bạn muốn tạo hàm kiểm tra đăng nhập:
[2940] Viết kiểm thử trước (ví dụ dùng Jest với JavaScript):
[2941] test('đăng nhập thành công với tài khoản đúng', () => {
  expect(login('user', 'pass')).toBe(true);
});
test('đăng nhập thất bại với tài khoản sai', () => {
  expect(login('user', 'wrongpass')).toBe(false);
});
[2942] Viết mã để kiểm thử vượt qua:
[2943] function login(username, password) {
  return username === 'user' && password === 'pass';
}

[2950] Các loại test
[2951] Unit Test: Kiểm tra từng “đơn vị” nhỏ nhất (hàm, class) một cách độc lập.
[2952] Ví dụ: Kiểm tra 1 hàm tính toán, 1 API xử lý đầu vào.
[2953] Integration Test: Kiểm tra sự phối hợp giữa các module, hoặc giữa app với DB, API ngoài.
[2954] E2E (End-to-End) Test: Kiểm tra toàn bộ luồng hoạt động, từ giao diện người dùng đến backend, database... như người dùng thật.
[2955] Thường kết hợp cả 3 loại để đảm bảo chất lượng toàn diện.
[2956] Performance Testing, Load Testing
[2957] Performance Testing: Đo hiệu năng hệ thống/app (tốc độ, độ trễ, throughput, sử dụng CPU/RAM...).
[2958] Load Testing: Đưa tải lớn (nhiều người dùng, request đồng thời) để xem hệ thống chịu được bao nhiêu trước khi chậm/hỏng.
[2959] Stress Testing: Đẩy quá tải để xem điểm gãy hệ thống.
[2960] Soak Testing: Chạy tải ổn định trong thời gian dài, tìm lỗi rò rỉ tài nguyên (memory leak...).
[2961] Công cụ phổ biến: JMeter, Gatling, Locust, k6, Artillery.

[2966] Được tích hợp trong GitHub/GitLab/Bitbucket Pull Request/Merge Request.
[2967] Lợi ích: Nâng cao chất lượng, chia sẻ kiến thức, giảm rủi ro.
[2968] Static Code Analysis
[2969] Là việc dùng công cụ tự động quét code để phát hiện lỗi, lỗ hổng, code xấu, vi phạm chuẩn coding, lặp code, bug tiềm ẩn...
[2970] SonarQube là công cụ rất phổ biến: hỗ trợ đa ngôn ngữ, phân tích code smell, bug, security hotspot, technical debt, v.v.
[2971] Thường tích hợp vào CI/CD để kiểm tra tự động, không cho phép merge nếu điểm chất lượng thấp.
[2973] Automation Testing (Selenium, Cypress)
[2974] Automation Testing là sử dụng các script/công cụ để tự động kiểm thử, thay vì thao tác tay.
[2975] Selenium: Thư viện automation test phổ biến nhất cho web application, hỗ trợ nhiều ngôn ngữ (Java, Python, C#, JS...), chạy trên nhiều browser.
[2976] Cypress: Framework hiện đại cho E2E testing web, dễ viết test, tích hợp CI/CD tốt, rất mạnh cho SPA/React/Vue/Angular.
[2977] Appium: Tự động test mobile app.
[2978] Lợi ích: Test nhanh, lặp lại nhiều lần, giảm công sức thủ công, tăng độ tin cậy.
